# Constitution

## Purpose

reco は、多数の GitHub リポジトリの設定状態を把握し、利用者の意図に沿って管理する負担を減らすために存在します。

## Problem Statement

GitHub の機能やセキュリティ設定は変化し続けています。多数のリポジトリを扱う利用者が、どのリポジトリでどの設定が有効なのかを記憶し、把握し続けることは困難です。そのため、利用者が対処すべきと判断する設定を見落としやすく、設定を確認・変更する作業にも負担がかかります。

## Value Proposition

reco は、利用者が意図する設定と GitHub 上の現在の設定との差を明らかにし、変更対象と内容を理解したうえで設定を適用できるようにします。これにより、個々の設定状態を記憶し続けなくても、複数のリポジトリを一貫した意図に沿って管理できます。

## Design Principles

### 現在の状態と変更内容の理解を、操作の効率より優先する

設定変更を効率化できても、現在の状態と意図する状態の違いや、変更による影響が分かりにくくなる設計は避けます。利用者が判断に必要な情報を把握できることを重視します。

### 暗黙の補完より、利用者の明示的な意図を優先する

推測や自動補完による利便性と、管理対象や変更結果の予測可能性が対立する場合は、後者を優先します。利用者が管理対象とした範囲を尊重します。

### 安全側の既定動作と、利用者によるリスク判断を両立する

セキュリティ上の影響に加え、reco 自身の不具合や想定外の動作による損害を考慮します。操作の効率より安全側の動作を基本としつつ、利用者が影響とリスクを理解したうえで選択する余地を尊重します。

### 目的に見合う単純さを、汎用性より優先する

実際の必要性が明らかでない抽象化や管理機構を追加して汎用性を高めるより、目的を満たす小さく理解しやすい構造を優先します。

## Non-Goals

reco は、リポジトリの設定を基にセキュリティリスクを独自に評価し、改善策を提案することを中核的な目的としません。設定の望ましさは基本的に利用者が判断します。

また、GitHub 上のあらゆるリソースや操作を統制する汎用管理基盤を目指しません。
