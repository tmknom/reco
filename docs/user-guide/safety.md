# Safety

## 書いていない設定を変えない

reco が変えるのは、設定ファイルに書いた設定だけです。

Environment も同じです。reco が作成するのも、`deployment_branch_policy` を変えるのも、設定ファイルに名前を書いた Environment だけです。Environment を削除することはありません。Ruleset も同じです。reco が作成するのも、内容を変えるのも、設定ファイルに名前を書いた Ruleset だけで、書いていない Ruleset は変更も削除もしません。

reco が削除するのは、設定ファイルに `state: absent` と書いた名前の Repository Variable、Environment Variable、Ruleset だけです。行を消した変数や Ruleset、書いていない変数や Ruleset は消しません。消す変数の値は、変更計画に `"<今の値>" -> absent` と示し、消す Ruleset は `present -> absent` と内容の全体を示して、承認を求めます。

書いた設定だけを変えるという原則の例外は、書いた設定を変えると GitHub の仕様でほかの値が消えるか変わる場合です。たとえば、`allowed_actions` を `selected` から `all` や `local_only` に変えると、GitHub が `selected_actions` の値を消します。`dependabot_alerts` を変えると、GitHub は Dependency graph も同じ値（有効か無効）に変えます。`dependabot_alerts` を無効にすると、GitHub は設定ファイルに書いていない Dependabot security updates も、有効だったなら無効にします。`secret_scanning` を無効にすると、GitHub は設定ファイルに書いていないリポジトリの push protection を、有効だったなら無効にします。reco はこれらを変更計画の `Side effect:` の行に示し、その内容も含めて承認を求めます。

`deployment_branch_policy.patterns` のように一覧を値とする設定では、書いた一覧が全体になり、GitHub 上の一覧にあって書いていない要素はなくなります。

## すべてのリポジトリを読み取ってから更新を始める

`apply` は、承認を求める前に、設定ファイル全体を読み、対象のすべてのリポジトリの設定を GitHub から読み取ります。設定ファイルに誤りがあるか、読み取れないリポジトリが一つでもあれば、どのリポジトリも更新せずに止まります。

読み取ったあとで、安全に変えるための条件が成り立たない変更（変更計画の `Applicability: not applicable` の行が付いた変更）が一つでもあれば、承認を求めず、どのリポジトリも更新せずに止まります。このとき reco は、そうした変更をすべてのリポジトリについて変更計画にまとめて示します。

## 承認した内容だけを変える

`apply` は、変更計画を表示して承認を求め、承認されるまで設定を変えません。承認のあとで、対象のリポジトリや変更の内容を差し替えることもありません。

## 承認のあとで設定が変わったら止まる

reco は、更新の直前ごとに、関係する設定が、承認したときの値（先に行った更新で予定どおりに変えた設定は、その変更後の値）のままかを確かめます。Environment、変数（Repository Variable と Environment Variable）、Ruleset を作成するときは、同じ名前（大文字と小文字だけが違う名前を含む）のものがまだないことを確かめます。承認のあとでほかの人や仕組みが設定を変えていたり、同じ名前の Environment、変数、Ruleset が作られていたりしたら、その更新もそのあとの更新も始めずに止まります。同じ名前の変数が作られていた場合は、その値が設定ファイルと同じでも止まります。変数を削除するときは、値が承認したときのままかを確かめ、変わっていれば消さずに止まります。既存の Ruleset の内容を置き換えるときは、変える予定の部分だけでなく、Ruleset の内容の全体が承認したときのままか、消されたり、別の名前に変えられたり、作り直されたりしていないかを確かめ、どれかが崩れていれば（ほかの人がルールや迂回できる主体を足しただけでも）置き換えずに止まります。Ruleset を削除するときも同じく確かめ、崩れていれば消さずに止まります。変数の削除と、Ruleset の置き換えと削除でこう確かめるのは、承認の前に示していない値を失わせないためです。それでも、`apply` のあいだに設定を変えられると、reco が見つけられないことがあります。たとえば、削除の直前の確認のあとに Ruleset の名前を変えられると、reco は承認したときの内容のその Ruleset を消し、完了と表示します。`apply` のあいだは、同じリポジトリの設定をほかの手段で変えないようにします。

## 問題が起きたら、それ以上更新しない

更新の失敗や、更新のあとの値が設定ファイルのとおりでないことなどを見つけたら、reco は残りの変更も、あとに並ぶリポジトリも更新しません。

## 反映を確かめてから完了とする

GitHub が更新を受け付けただけでは、reco は完了（`updated`）としません。設定を読み直して、設定ファイルのとおりになっていることと、その更新で一緒に変わり得る設定が、`Side effect:` に示したものを除いて変わっていないことを確かめてから完了とします。

## トークンを表に出さない

reco は、渡されたトークンを GitHub へのアクセスにだけ使います。トークンをファイルに保存せず、出力やエラーにも表示しません。

`show` は Repository Variables と Environment Variables の値をそのまま表示し、変更計画は、設定ファイルに書いた Repository Variables と Environment Variables の今の値と書いた値を表示します。reco はこれらの値を秘密情報として扱いません。GitHub も Variables を機密でない設定値の保存先としているためです。秘密情報は Variables ではなく Secrets に入れます。

## reco がしないこと

- **変更を元に戻さない**：`apply` が途中で止まっても、すでに反映した変更はそのまま残る。元に戻すときは、元の値を書いて `apply` する。作成した Environment は GitHub 上で消し、作成した Ruleset は `state: absent` を書いて `apply` するか GitHub 上で消し、設定ファイルに書けない設定（Dependency graph など）は GitHub 上で元の値に戻す。内容を置き換えた Ruleset が、置き換える前に設定ファイルに書けない値（`enforcement: evaluate` や `conditions: {}` など）を持っていたときも、GitHub 上でその値に戻す
- **成否が分からない更新を送り直さない**：GitHub が更新を受け付けたか分からないときは、送り直さずに止まる。`plan` で今の値を確かめてから `apply` し直す
- **外部のクラウドなどの設定を確かめない**：OIDC トークンの subject の形を変えたとき、`updated` が示すのは GitHub 上の設定値が設定ファイルのとおりになったことまでで、外部のクラウドなどでワークフローが認証できることではない。reco は外部の信頼の条件を読まず、変えない
- **リダイレクトに従わない**：名前を変えたか移転したリポジトリを古い名前で指定すると、意図しない宛先へトークンを送らないよう、エラーで止まる

`apply` が止まったときにすることは [Troubleshooting](troubleshooting.md) にあります。
