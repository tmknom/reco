# reco の安全性の約束

reco は、利用者の承認と GitHub 上の状態の確認を条件にして、リポジトリの設定を変えます。利用者が自分で確かめる必要のあることは、最後の「reco が引き受けないこと」にまとめています。用語の意味は [用語集](glossary.md) にあります。

## 宣言していない設定を変えない

reco が変更の対象に選ぶのは、管理設定だけです。未管理設定を、reco の更新操作で変えたり消したりしません。GitHub の都合で未管理設定の今の値も一緒に送る必要があるときは、その値を保てると確かめられなければ、その更新を始めません。

たとえば `general` に `allow_auto_merge` だけを書いたリポジトリでその値を変えるとき、reco が GitHub に送るのは `allow_auto_merge` の値だけです。リポジトリの名前、説明、公開範囲などのほかの一般設定は送りません。

例外は、宣言した変更に伴って、GitHub の仕様で未管理設定の値が避けられずに消える場合です。現在は、Actions 許可ポリシーを `all` か `local_only` にする変更で、GitHub が `selected_actions` の値を消す場合がこれに当たります。reco はこの変更を止めず、消える値か、値を読み取れないときは消える可能性を、副作用として変更計画に示し（[`Side effect:` の行](reading-output.md#副作用)）、その副作用も含めて承認を求めます。どんなときに何が消えるかは [設定ファイルの書き方](configuration.md#actions-許可ポリシーを変えるときに起きること) にあります。

## 全リポジトリを確かめてから更新を始める

`apply` は、承認を求める前に、設定ファイル全体を検証し、対象にしたすべてのリポジトリの設定を GitHub から読み取り、安全に変えられるかを判断し終えます。設定ファイルに誤りがあれば GitHub に問い合わせる前に止まり、読み取りに失敗したリポジトリが一つでもあればその時点で止まります。安全に変えるための条件が成り立たないか、成り立つと確かめられない変更予定が見つかったときも、すべてのリポジトリを確かめ終えてから止まります。どの場合も、どのリポジトリも更新しません。

たとえば三つのリポジトリを並べ、三つ目の読み取りが権限の不足で失敗したとします。一つ目と二つ目に変更予定があっても、reco は承認を求めず、どのリポジトリも更新せずに終わります。

## 承認した内容だけを実行する

`apply` は、変更計画を表示してから承認を求め、利用者が端末で承認するまで更新を始めません。承認を省略するオプションはありません。承認として受け付ける入力と、承認を求めない場面は [コマンドリファレンス](commands.md#承認) にあります。

承認が及ぶのは、その `apply` が表示した変更計画だけです。承認のあとで、reco が対象のリポジトリや変更内容を差し替えることはありません。

## 承認のあとで状況が変わったら止まる

reco は、更新操作の直前ごとに変更前提（対象が承認したリポジトリと同じであることや、関係する設定が承認したときに予定した値のままであること）を確かめます。全リポジトリの事前の確認のあとにも、GitHub の状態は変わり得るためです。成り立つと確かめられなければ（読み取りに失敗した場合を含む）、その更新操作も、そのあとの更新操作も始めません。

たとえば三つのリポジトリの `allow_auto_merge` を変える `apply` で、reco が一つ目を更新しているあいだに、ほかの人が GitHub の設定画面で二つ目の `allow_auto_merge` を変えたとします。reco は二つ目を未実行（`not attempted`）とし、承認のあとに値が変わった設定を示します（[`Precondition:` の行](reading-output.md#更新を始めなかった理由)）。

## 異常を見つけたら、それ以上更新しない

reco は、次のどれかを見つけたら、その `apply` では新しい更新を始めません。

- 更新操作の失敗
- 更新操作の成否不明
- 変更前提の不成立
- 更新のあとに期待状態を確かめられないこと、または期待状態と一致しないこと
- 変更対象外の設定の予期しない変化

同じリポジトリの残りの変更も、あとに並ぶ変更予定のあるリポジトリも更新せず、未実行（`not attempted`）として、先の異常で止めたことを示します（[`Stopped:` の行](reading-output.md#更新を始めなかった理由)）。たとえば三つのリポジトリの一つ目が失敗（`failed`）に終われば、二つ目と三つ目には更新要求を送りません。

## 反映を確かめてから完了と報告する

GitHub が更新を受け付けたと応答しても、reco はそれだけで完了（`updated`）としません。完了とするのは、必要な更新操作が成功し、読み取り直した設定が期待状態になっていて、変更対象外の設定の予期しない変化も（読み取り直せる範囲で）見つからなかったときだけです。成否不明の更新操作は、読み取り直して期待状態と一致しても完了にしません。完了を確かめられなければ、失敗（`failed`）です。

たとえば `delete_branch_on_merge` を変えたあと、同じリポジトリの `allow_auto_merge` も変わっていたとします。`delete_branch_on_merge` が期待値になっていても、reco は完了とせず失敗にします。ほかの人が同じ時刻に変えた可能性もあるため、reco は変化の原因を断定しません。

## 認証情報を表に出さない

reco は、`GH_TOKEN` か `GITHUB_TOKEN` で渡されたトークンを、GitHub の API への要求にだけ使います。トークンをファイルに保存せず、正常に終わったときも異常で止まったときも、出力、エラー、ログに表示しません。たとえば認証に失敗したときのエラーも、トークンの値を含まず、`401` などの応答の状態を示します。

## reco が引き受けないこと

### 変更を自動で元に戻さない

`apply` が途中で止まっても、reco はすでに反映した変更を元に戻しません。元に戻す操作も GitHub への新しい更新であり、reco は異常を見つけたあとは新しい更新を始めないためです（「異常を見つけたら、それ以上更新しない」）。止まったあとは、`plan` で今の状態を確かめ、欲しい値を設定ファイルに書いて `apply` し直します。元の値に戻す手順は [複数リポジトリの運用](operations.md#変えた値を戻す) にあります。

### 成否が分からない更新を再送しない

更新要求への応答が途中で失われた場合などは、GitHub が更新を受け付けたかどうかが分かりません（成否不明、`unknown`）。reco はこの更新要求を送り直しません。成否不明も「異常を見つけたら、それ以上更新しない」の異常の一つであり、送り直すことは、最初の要求が反映されたかどうかを確かめないまま更新を重ねることになるためです。`plan` で今の状態を確かめ、必要なら `apply` し直します。

### リダイレクトに従わない

名前を変えたか移転したリポジトリを古い名前で指定すると、GitHub は新しい場所へ案内する応答（リダイレクト）を返します。reco はこの案内に従わず、エラーで止まります。従うと、利用者が確かめていない宛先へトークンを送ったり、意図しないリポジトリを更新したりするおそれがあるためです。名前を変えたか移転したときは、設定ファイルの `name` を今のオーナーと名前に書き直します。

### ほかの人や自動化による同時の変更は防げない

reco が守るのは reco 自身の更新操作であり、ほかの人や自動化が同じ時刻に設定を変えること自体は止められません。更新の直前の確認と更新のあいだや、更新のあとの確認より後に起きた変更を、reco は見つけられません。同時の変更を避ける手順と、止まったときにすることは [複数リポジトリの運用](operations.md#ほかの人や自動化と同時に変えるとき) にあります。

### 二つの更新操作からなる変更の途中で止まると、中間状態が残る

Actions 許可ポリシーを、`all` か `local_only` か、Actions が無効の状態から `selected` にする変更は、二つの更新操作からなります。二つ目の更新操作を始められなかったとき、または二つ目が拒否されたか成否不明になったときは、宣言していない許可を含み得る中間状態が残ることがあります。このとき `apply` は失敗（`failed`）になり、どの更新操作まで終えたかが示されます（[`Update request` の行](reading-output.md#更新操作の結果と期待状態の確認結果)）。中間状態がどんな値になるかは [設定ファイルの書き方](configuration.md#all-や-local_only-から-selected-に変えるとき) にあります。`plan` で状態を確かめ、`apply` し直すか、GitHub の設定画面で直します。

### 設定の良し悪しを判断しない

reco は、設定ファイルに書いた値がセキュリティ上望ましいかを評価せず、書いた値のとおりに変えます。どの値にするかは利用者が決め、承認の前に変更計画で確かめます。
