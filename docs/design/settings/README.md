# 設定ごとの設計

## 目的と適用範囲

本ディレクトリでは、reco が扱う設定について、その設定に固有の設計を管理します。どの読み取り要求で読み、応答をどう解釈するか、どの変更予定が適用可能で、どの副作用を示すか、変更予定をどの更新操作にどの順で分けるか、何を送り、何を比べて未管理設定を保全するかです。

概念の意味は [ドメインモデル](../domain.md) に、すべての設定に共通する処理の仕組みは [アーキテクチャ設計](../architecture.md) に、その細則のうち GitHub への要求と応答の解釈（取得契約、リポジトリの読み取り、一覧の読み方、名前を含む宛先、更新操作の結果の判定）は [GitHub API 通信の設計](../github-access.md) に、承認後の観測し直しと更新要求の間隔は [変更の実行の設計](../execution.md) に従い、ここでは繰り返しません。二つの文書と本ディレクトリの分け方は、[ドキュメント規約](../../contributing/docs-policy.md) 1章が定めます。

## 文書の分け方

文書は、設定宣言のトップレベルのキー（[YAML 設定仕様](../../spec/configuration.md) 1章）ごとに一つ作ります。一つの文書は、そのキーに属するすべての設定の領域を扱います。

| 文書 | トップレベルのキー | 扱う設定の領域 |
|---|---|---|
| [General の設計](general.md) | `general` | General |
| [Actions の設計](actions.md) | `actions` | Actions の実行許可、ワークフロー権限、リポジトリ外のワークフローからのアクセス、Repository Variables |
| [Environments の設計](environments.md) | `environments` | Environments、Environment Variables |
| [Security の設計](security.md) | `security` | Dependabot、Secret scanning、Private vulnerability reporting |

設定の領域ごとではなくトップレベルのキーごとに分けるのは、同じキーの設定どうしが、観測の条件や更新の順序で互いに依存し、一緒に変わるためです。Actions の各領域は Actions の有効状態と公開範囲を読み分ける条件を、Security の各領域は前提の設定と依存する設定の扱いと、公開範囲による観測不能を共有します。キーをまたぐ依存（General と Secret scanning が同じ更新エンドポイントを使うこと）は、それぞれの文書が自分の更新操作について書き（更新後に比べる、もう一方のキーの設定など）、もう一方の設定の規則は参照します。

## 文書の構成

各文書は、次の節をこの並びで持ちます。読者が設定と知りたいこと（どう読むか、なぜ適用不能か、どう更新するか）の組から、節の名前で探せるようにするためです。その設定に固有の内容がない節は置きません。節の名前は Go のコメントが参照するため、変えるときは参照元も直します。

| 節 | 書くこと |
|---|---|
| 設定と管理の単位 | 領域に属する設定の用語、管理の単位と設定グループ、期待値が含む状態、値の比べ方 |
| 観測 | 読み取り要求と送る条件、取得契約、取得条件による観測不能、観測操作の失敗として扱う応答 |
| 適用可能性と副作用 | 変更予定ごとの適用可能性、変更に伴う副作用、副作用を示さなかった設定、再開する設定 |
| 論理的な設定変更と更新操作 | 変更予定の論理的な設定変更へのまとめ方、更新操作の順序、変更前提で比べる関係する現在値と承認時に予定した値、中間状態 |
| 更新方式 | 送るフィールド、正常応答、未管理設定を保全する根拠、更新後に比べる変更対象外の設定 |
| シナリオと反例 | その設定に固有の事実がなければ解釈を誤る例 |

何を書き、何を書かないかは [ドキュメント規約](../../contributing/docs-policy.md) 1章が定めます。GitHub の事実は [GitHub API 仕様](../../research/README.md) を根拠とし、各節の Relationship テーブルの `grounding` で示します。
