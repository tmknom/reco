# GitHub API 通信の設計

## 1. 目的と適用範囲

本ドキュメントは、[アーキテクチャ設計](architecture.md) の GitHub Access が、すべての設定に共通して GitHub REST API へ要求を送り、応答を解釈する規則を定めます。読み取り要求の応答から観測結果を作る規則、リポジトリリソースの一覧の読み方、更新要求の応答から更新操作の結果を決める規則、リポジトリリソースの名前を宛先に入れる規則、読み取りの再試行です。送信先の限定とリダイレクトの扱いはアーキテクチャ設計 5.2節が、設定ごとの読み取り要求・取得契約のフィールド・正常応答は [設定ごとの設計](settings/README.md) の各文書の「観測」と「更新方式」が、GitHub の事実は [GitHub API 仕様](../research/README.md) が定めます。

### 2.1 取得契約

API の成功応答を受け取ったことだけでは、必要な設定値を確認できたとは判断しません。必要なフィールドが得られない場合、GitHub の既知の取得条件による観測不能と根拠をもって分類できるときに限り、観測結果にその理由を記録します。読み取り要求の成功応答に期待するこの形を **取得契約** と呼びます。本文を解釈でき、観測に必要なフィールドが、既知の取得条件による欠落を除いてそろっていることです。理由を確認できない欠落や解釈できない本文のように、取得契約に適合しない応答は観測操作の失敗として扱います。欠落した値を既定値で補ったり、理由を推測して比較不能へ置き換えたりしません。

GitHub が種類を増やし得る要素（種類を表すフィールドで形が決まる配列の要素など）では、reco の扱わない種類と、扱う種類の reco の知らない項目を、取得契約に適合しない応答にしません。その要素を含む設定を、値が解釈しない部分を含むことを理由とする観測不能とします（[ドメインモデル](domain.md) の現在状態・観測結果・観測失敗）。一方、reco の扱う項目の型が合わないこと、種類を表すフィールドの欠落、必須のフィールドの欠落は、取得契約に適合しない応答のままです。どの要素をこの形で読むかは、設定ごとの設計の「観測」が定めます。

GitHub は API バージョンを変えずに列挙の値を足すため（[GitHub REST API 共通仕様](../research/rest-api.md) 2章）、列挙の値を持つフィールドが reco の知らない文字列を返しても、取得契約に適合しない応答にしません。その値を持つ設定を、値が知らない値であることを理由とする観測不能とします。公式の仕様が省略を許すフィールドが応答にないときも同じく、その設定を、省略を許された値が返らなかったことを理由とする観測不能とします（[ドメインモデル](domain.md) の現在状態・観測結果・観測失敗）。型が文字列でない値や、`null` は、取得契約に適合しない応答のままです。要素の配列が列挙のフィールドを持つときは、すべての要素を取得契約と照らしたうえで、知らない文字列を持つ要素が一つでもあれば、その配列を値とする設定を同じ理由の観測不能とします。同じ応答が取得契約に適合しない部分も含むときは、取得契約に適合しない応答です。省略を許されないフィールドの欠落は、知らない文字列と同じには扱いません。GitHub は、列挙の値の追加を追加的な変更とする一方、応答のフィールドの削除を破壊的変更として新しい API バージョンで行うとしており（同 2章）、欠落は権限の不足でも同じ形になって、応答からは原因を区別できないためです。どのフィールドをこの形で読むかは、設定ごとの設計の「観測」が定めます。この形で読まないフィールドの知らない値は、取得契約に適合しない応答のままです。

成功応答の本文は上限の大きさまで読み、超えた本文は取得契約に適合しない応答とします。上限は、異常な応答を読み続けないためのものです。上限は 1 MiB とし、GitHub の制限から1ページの最大の大きさを導けて、それが 1 MiB を超える一覧に限り、導いた大きさを上限にします。1ページの上限を上げる一覧では、異常な応答で読み続ける総量を抑えるため、ページ数の上限も導いた値にします。導いた上限を持つ一覧と、その導出は設定ごとの設計の「観測」が定めます。

### 2.2 観測の要求の順序

どの観測も、リポジトリ ID を読むために `GET /repos/{owner}/{repo}` を最初に送り、ほかの読み取り要求は、それが成功したときだけ送ります。いずれかの要求が失敗すれば観測操作の失敗であり、取得できた値だけの観測結果は作りません。一回の観測で複数の設定の領域を読むときは、[YAML 設定仕様](../spec/configuration.md) の章の並びで設定の領域を読みます。

この最初の要求の取得契約は、読む設定の領域によらず、`id` と、リポジトリの公開範囲を表す `private` がそろうことです。欠けた `private` を公開とみなすと、公開範囲を取得条件とする設定に、根拠のない観測不能を作るためです。リポジトリへの admin のアクセスを表す `permissions` は取得契約に含めず、欠けていても `null` でも失敗しません。値の読み方に `permissions` を使う設定の領域だけが、その欠落の扱いを設定ごとの設計の「観測」で定めます。ただし、型の合わない `permissions`（オブジェクトでない、`admin` が boolean でない）は解釈できない本文であり、どの観測でも取得契約に適合しない応答とします。

### 2.3 リポジトリリソースの一覧の読み方

リポジトリリソースが存在しないことは、その種類の一覧の成功応答に名前がないことで確かめます。名前を指定した取得に対する `404` は、権限の不足でも返り得るため、存在しないことの確認に使いません。一覧は全ページを読みます。途中のページの読み取りが失敗した場合は観測操作の失敗であり、読めたページだけの観測結果は作りません。読めた範囲に名前がないことから、存在しないとは判断しません。一覧の成功応答が、その種類のリポジトリリソースをすべて含むことも、種類ごとに実際の動作で確かめます。一覧に名前があるかどうかは、GitHub がその種類で名前を同じとみなす規則（大文字と小文字を区別するかなど）で判定します。この規則を実際の動作で確かめていない種類では、一覧に名前がないことから存在しないとは判断しません。規則を誤ると、存在するリポジトリリソースを存在しないと判断し、作成の要求で上書きし得るためです。

一覧は、`per_page` にその一覧で GitHub が受け付ける上限を、`page` に `1` から順の番号を付けて読みます。上限は多くの一覧で `100` で、それと異なる一覧の値は設定ごとの設計の「観測」が定めます。応答の `total_count` を全件数とし、読んだ要素の数が `total_count` に達したら読み終えたとします。達するまでは次のページを読み、次の場合は観測操作の失敗とします。

- 要素が一つもないページを、全件に達する前に受けた
- 読んだ要素の数が `total_count` を超えた
- `total_count` が、同じ一覧の1ページ目と異なった
- ページ数の上限まで読んでも全件に達しない
- `total_count` か要素の配列が欠けた

件数が食い違う一覧は、読んでいるあいだにリポジトリリソースが増減した可能性があり、ページの境目で要素を読み落とし得るためです。件数が変わらない入れ替わり（1件が消え、1件が増えた）は検出できません。次のページへの要求は、reco が組み立てた `/repos/{owner}/{repo}/...` の URL にだけ送り、応答の `Link` ヘッダーは読みません。`Link` の URL は `/repositories/{repository_id}/...` の形で reco が組み立てる URL と異なり（[GitHub デプロイ環境 API 仕様](../research/deployment-environments.md) 3.1）、たどると送信先を応答の内容に委ねることになるためです（[アーキテクチャ設計](architecture.md) 5.2節）。ページ数の上限は、異常な応答で要求を送り続けないためのもので、多くの一覧で100ページです。宣言を受け付けない種類のリポジトリリソースの一覧（削除の副作用を示すために読む、属するリポジトリリソースの一覧など）も、同じ読み方で読みます。読み落とした要素は、承認の前に示さないまま失わせることになるためです。

`total_count` を返さず、要素の配列だけを返す一覧もあります。この一覧は、要素の数が `per_page` に満たないページを最後のページとし、`per_page` ちょうどの要素を返したページのあとは次のページを読みます。要素が一つもないページも最後のページです。ページ数の上限まで読んでも最後のページに達しない場合と、本文が配列でない場合は、観測操作の失敗とします。この読み方は、読んでいるあいだの増減でページの境目の要素を読み落としても検出できません。そのため、GitHub が公式資料で示す件数の上限が `per_page` の上限より小さい一覧に限って使い、1ページ目で読み終えるようにします。どの一覧がこの形かと、その上限は設定ごとの設計の「観測」が定めます。

### 2.4 リポジトリリソースを読む範囲

リポジトリリソースの一覧は、その種類が属する設定の領域を読み取る観測でだけ読みます。`show` は宣言を受け付けるすべての種類の一覧を読み、`plan` と `apply` は宣言された設定の領域の一覧だけを読みます。宣言を受け付けない種類で、削除の副作用を示すためだけに読む属するリポジトリリソースの一覧は、`plan` と、`apply` の更新直前の観測で、存在しないことを宣言された属する先のリポジトリリソースが一覧にあるときだけ、その属する先について読みます。`show` は読みません。`show` は宣言できるものだけを示し（[表示仕様](../spec/output.md) 5.1節）、この一覧を使わないためです。削除のあとの更新後の観測も読みません。確かめるのは属する先が存在しないことだけだからです。別のリポジトリリソースに属するリポジトリリソースは、属する先が存在すると確かめたときだけ読み、存在しないときは、属する先が存在しないことを理由とする観測不能とします。属する先と別の設定の領域に属する種類は、属する先の種類の一覧（その中のリポジトリリソースの一覧を含む）を読み終えてから読みます。

リポジトリリソースごとに送る読み取り要求（リポジトリリソースの値の読み取り、リポジトリリソースの中の設定の読み取り、それに属するリポジトリリソースの一覧）は、その種類の一覧を全ページ読んだうえで、観測を使う側が名指したリポジトリリソースにだけ送れます（どの観測がどのリポジトリリソースに送るかは [ドメインモデル](domain.md) の現在状態・観測結果・観測失敗）。名指した名前と一覧の名前が同じかどうかは、存在の判定と同じ規則で決めます。どの種類で範囲を限るかは、設定ごとの設計の「観測」が定めます。

### 3.1 更新操作の結果の判定

更新操作の成功・失敗・成否不明は、GitHub Access が更新要求への応答から次のとおり判定します。Change Execution はこの判定を読み替えません。

| 更新要求への応答 | 更新操作の結果 |
|---|---|
| 更新エンドポイントの正常応答を受け取り、応答が更新の契約に適合した | 成功 |
| `4xx`（認証失敗、権限不足、レート制限、対象が見つからない、処理できない要求、競合、その他の `4xx`） | 失敗 |
| `5xx` | 成否不明 |
| `3xx`（リダイレクト応答） | 成否不明 |
| 応答を受け取れなかった（接続の失敗、時間切れ、中断） | 成否不明 |
| 正常応答の本文を最後まで受け取れなかった、または応答が更新の契約に適合しない | 成否不明 |
| 更新エンドポイントの正常応答以外の `2xx`、最終応答としての `1xx` | 成否不明 |

`4xx` だけを失敗とするのは、GitHub が要求を拒否したと応答したステータスだからです。`5xx` は拒否を表さず、更新が処理されたかを応答から判断できないため、reco は成否不明とします。

更新エンドポイントの正常応答とは、[GitHub API 仕様](../research/README.md) がその更新エンドポイントの正常応答として記載したステータスです。成功とする `2xx` を正常応答に限るのは、GitHub がドキュメントで正常応答として示したステータスでなければ、更新要求を処理した応答だと根拠づけられないためです。正常応答のステータスは更新エンドポイントによって異なり、設定ごとの設計の「更新方式」が定めます。

### 3.2 更新の契約

成功の判定に使う **更新の契約** は、正常応答の本文がリソースの表現を返すかどうかで次のように定まります。

- **本文がリソースの表現を返す正常応答**：本文を解釈でき、その設定の取得契約と同じフィールドがそろっている。取得契約と異なり、欠落を取得条件による観測不能とはみなさない
- **本文がリソースの表現を返さない正常応答**：本文がないか、リソースを含まない本文（空のオブジェクトなど）を返す。本文で確かめる値はなく、本文を解釈しない

更新の成功応答で確かめるのは値ではなく、GitHub が更新要求を処理した応答であることです。更新後の値とリポジトリ ID は、更新後の期待状態の確認で再取得して確かめます。

## 4. リポジトリリソースの名前を含む宛先

リポジトリリソースの名前を読み取り要求か更新要求のパスに入れるときは、名前をパスの一つの要素としてエスケープします。エスケープしない `/` は、別の経路への要求になるためです。`.` と `..` はエスケープしても別の経路を指すため、その名前を宛先とする要求は送らず、読み取りなら観測操作の失敗とします。どの種類の名前がパスに入るかと、宛先に使う綴り（宣言の綴りか、観測の綴りか）は、設定ごとの設計の「観測」と「更新方式」が定めます。

## 5. レート制限と読み取りの再試行

読み取り操作のリトライは、対象オリジンの制約と回数・待機時間の上限を守り、再試行可能な一時的失敗に限定します。認証失敗や対象の不明確さをリトライで補いません。レート制限時は GitHub の指示する待機条件を守ります。読み取りの再試行は、更新要求の再送を認める根拠になりません。

レート制限の超過は `403` または `429` で報告され、ステータスコードだけでは権限不足と区別できません。GitHub Access は `retry-after` と `x-ratelimit-remaining` の応答ヘッダーからレート制限かどうかを判定し、レート制限による `403` を権限不足と断定しません。
