# 変更の実行の設計

## 1. 目的と適用範囲

本ドキュメントは、[アーキテクチャ設計](architecture.md) の Change Execution が、承認後に更新操作を進めるときの観測し直しと待機の規則を定めます。GitHub の反映の遅れに備えて観測し直す条件・間隔・回数、止まったあとに行う観測、更新要求の間隔です。後続の更新を止める条件と、更新要求を再送しないことはアーキテクチャ設計 6章が、観測の時点ごとの意味と、どの観測が確認結果を与えるかは [ドメインモデル](domain.md) の現在状態・観測結果・観測失敗が定めます。

ここで定める観測し直しと待機は、どれも後続の更新操作を開始しない条件を減らさず、更新要求を再送せず、更新操作の結果を変えません。

## 2. 更新後の観測し直し

GitHub は、更新要求に正常応答を返したあと、すぐには取得の結果に更新を反映しないことがあります（[GitHub Actions 権限 API 仕様](../research/actions-permissions.md) 5.2）。どの設定と条件で反映が遅れるかは公式ドキュメントに記載がないため、Change Execution はすべての更新操作について、反映が遅れ得るものとして扱います。更新操作が成功または成否不明に終わったら、待たずに更新後の観測を行います。更新操作が成功し、観測値が期待状態と一致しないとき、または期待値と比べる設定が観測不能のときに限り、1秒、2秒、4秒、8秒、16秒と間隔を倍にして待ちながら観測し直します。反映がすぐに済む場合に待ち時間を足さず、遅れた場合も読み取り要求を続けて送らないためです。期待状態との一致を確認できた時点でやめ、6回目の観測でも一致を確認できなければ、その観測が与える確認結果（不一致または確認失敗。[ドメインモデル](domain.md) の期待状態の確認結果）とします。観測不能のときも観測し直すのは、Actions が無効の状態から有効にする更新では、更新前の値を返す取得が、外部主体が Actions を無効にした場合と同じ応答になるためです。

観測操作の失敗とリポジトリ ID の不一致では、その時点で期待状態の確認失敗とします。前者は読み取りの失敗で、読み取りの再試行の規則（[GitHub API 通信の設計](github-access.md) 5章）が扱います。後者は反映の遅れでは説明できないためです。待っているあいだに中断を受けたら、観測せずに期待状態の確認失敗とします。

## 3. 後続の更新操作の直前の観測し直し

一つの論理的な設定変更が複数の更新操作からなるとき、先行する更新操作の反映の遅れは、後続の更新操作の直前の観測にも現れ得ます。先行する更新操作が成功し、後続の更新操作の直前の観測が先行する更新操作の変更前提をそのまま満たすとき（先行する更新操作が変える設定が、その更新直前の値のまま、または同じ理由で観測不能のままのとき）に限り、更新後の観測と同じ間隔で待ちながら観測し直します。後続の更新操作の変更前提が成立した時点でやめ、6回目の観測でも先行する更新操作の直前の状態のままなら、関係する現在値の変化として変更前提の不成立とし、後続の更新操作を開始しません。観測し直すのは、反映の遅れだけを理由に、反映済みの先行する更新操作と中間状態（[アーキテクチャ設計](architecture.md) 5.4節）を残して止まる頻度を下げるためです。

後続の更新操作を開始するのは、観測し直さない場合と同じ変更前提が、最後の観測で成立したときだけです。先行する更新操作が失敗または成否不明に終わった場合は、この観測そのものを行わず、成否不明のあとの診断の観測で予定どおりの値が見えても後続の更新操作を開始しません。観測操作の失敗、リポジトリ ID の不一致、先行する更新操作の直前の値でも承認時に予定した値でもない値の観測では、観測し直さずに、その時点で変更前提の不成立とします。最後の場合は反映の遅れでは説明できないためです。待っているあいだに中断を受けたら、観測せずに変更前提の確認不能とします。

この観測し直しは、同じ論理的な設定変更の先行する更新操作に限ります。先行する別の論理的な設定変更は、更新後の観測で期待状態を確かめて完了しているためです。

## 4. 止まったあとの観測

更新操作が成否不明に終わったら、診断のために更新後の観測を一度だけ行い、一致しなくても観測し直しません。2章の観測し直しは、更新操作が成功した場合に限るためです。

先行する更新操作が成功したあとで、後続の更新操作を開始できなかった場合と、後続の更新操作が失敗した場合も、更新後の観測を一度だけ行います。先行する更新操作が GitHub の状態を変えているため、期待状態の確認結果と、先行する更新操作の更新エンドポイントの変更対象外の設定の予期しない変化を示すためです（FR-012）。完了を確認できないことはすでに決まっているため、観測し直しません。最初の更新操作が失敗した場合は、更新後の観測を行いません。

## 5. 更新要求の間隔

GitHub は、セカンダリのレート制限を避けるため、大量の更新系の要求を送るときは要求のあいだを少なくとも1秒空けるよう推奨しています（[GitHub REST API 共通仕様](../research/rest-api.md) 5章）。Change Execution は、一回の実行で更新操作を一つでも開始したあとは、次の更新操作の更新直前の観測より前に1秒待ちます。この待機を **更新要求の間隔** と呼びます。待つのは、先行する論理的な設定変更の更新後の観測と次の論理的な設定変更の最初の更新操作の更新直前の観測のあいだと、複数の更新操作からなる論理的な設定変更の、先行する更新操作の更新要求と後続の更新操作の更新直前の観測のあいだです。先行する論理的な設定変更と次の論理的な設定変更が別の対象リポジトリに属する場合も同じで、あいだに変更不要の対象リポジトリをはさんでも、待つのは一度です。最初の更新操作の前と、最後の更新操作のあとは待ちません。更新要求のあいだの時間は、この1秒に更新直前の観測の読み取りの時間が加わるため、1秒以上になります。経過時間を測って不足分だけ待つことはしません。

更新直前の観測より前に待つのは、観測のあとに待つと、変更前提を確かめてから更新要求を送るまでの時間が延び、そのあいだの外部主体の変更を見逃すためです。後続の更新操作では、待ったあとの最初の観測から、3章の観測し直しの規則をそのまま適用します。更新要求の間隔は、観測し直しの回数と待つ時間に数えません。

待つのは次の更新操作の更新直前の観測へ進む場合だけで、待ったあとに確かめる変更前提は変わりません。先行する論理的な設定変更が完了以外に終わった場合と、先行する更新操作が成功しなかった場合は、待たずに後続を停止します。待っているあいだに中断を受けたら、観測せずに変更前提の確認不能とし、その更新操作を開始しません。
