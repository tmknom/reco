# ドキュメント規約

本ドキュメントは、reco リポジトリの文書を読み、変更するための共通規約を定めます。文書が規定する情報の責務、識別子、Relationships、変更時の参照方法、ユーザーガイドの書き方を対象とします。

## 1. 文書の責務と正本

正本とは、ある情報の意味を確定・変更するときに優先する定義です。文書の詳しさや作成順序ではなく、規定する内容によって正本を区別します。

| 文書 | 主な責務 |
|---|---|
| Constitution | reco の存在理由、解決する問題、提供価値、設計判断の原則 |
| 要求定義 | 提供する機能、必要な振る舞い、品質、保証、適用範囲 |
| CLI 仕様 | コマンド、オプション、認証情報の選択、表示、終了コードなどの外部契約 |
| YAML 設定仕様 | 設定宣言の構造、型、許容値、入力検証などの外部契約 |
| ドメインモデル | リポジトリ設定の管理に関する概念とその関係 |
| アーキテクチャ設計 | システムの論理構成、責務、依存関係、主要な処理の仕組み |
| GitHub API 仕様 | reco が利用する GitHub REST API の外部契約を、GitHub の公式資料から抜粋・整理したもの。`docs/research/` の複数の文書からなる |
| ユーザーガイド | 利用者の目的に沿った、正本の説明。`docs/user-guide/` の複数の文書からなる。規則の正本ではない（5章） |

用語の意味は、ドメインモデルを正本とします。ほかの文書で用語を導入するときは、意味を変えずに要約します。

GitHub API の契約は GitHub の公式資料が正本です。開発のたびに公式資料を参照しなくて済むよう、必要な事実は [GitHub API 仕様](../research/README.md) に抽出します。GitHub API 仕様を構成する文書と、事実をどの文書に書くかは、GitHub API 仕様の README が定めます。GitHub API 仕様は GitHub の公式資料だけを根拠とし、ほかの内部文書に依存せず単独で読めるようにします。ただし、公式資料の記載が不十分で、reco の開発者が実際の動作を確認した事項は、公式資料の記載と区別できる注釈として記載できます。依存の向きは一方向であり、ほかの内部文書が GitHub API の事実を根拠とするときは GitHub API 仕様を参照し、GitHub API 仕様からほかの内部文書は参照しません。スクリプトは文書ではないため内部文書に含まず、GitHub API 仕様から参照できます。GitHub API 仕様に必要な事実がなければ、公式資料で確認して GitHub API 仕様に追記してから参照します。

reco の要求・契約・設計における独自の判断と、GitHub が定めた事実を区別します。GitHub の事実をどう扱うかは参照する側の文書で定め、GitHub API 仕様には書きません。同じ規則を複数文書で独立して定義せず、必要な箇所から正本を参照します。

## 2. 識別子

要求や不変条件などの定義を安定して参照するため、次の識別子を使います。

| 形式 | 対象 |
|---|---|
| `FR-001` | 機能要求：提供する能力、振る舞い、重要な操作上の保証 |
| `QR-001` | 品質要求：検証可能な品質上の性質・制約 |
| `INV-001` | 不変条件：適用範囲内で維持すべき状態・遷移の性質 |

識別子は定義見出しの先頭に置きます。プレフィックスごとに3桁以上の連番を使い、識別対象とした情報種別では重要度にかかわらず全定義に付与します。説明や具体例には、独立した定義でない限り新しい識別子を付けません。

要求定義の「機能要求」「品質要求」「不変条件」の各章では、直下の見出しをすべて識別子付きの定義見出しとします。分類のための見出しを同じ階層に置きません。

識別子が表すのは定義の同一性であり、ファイルの位置や検証状況ではありません。定義の責務が継続するなら、見出しや配置が変わっても識別子を維持します。意味を変更した場合は、識別子を維持しても参照元を再確認します。識別子を変更する場合は、リポジトリ全体に変更を反映し、一貫性が保たれるようにします。

定義を削除・分割・統合するときは、次の規則に従います。

- **削除した識別子の再利用**：削除前の意味への参照が、リポジトリ内にも、コミットメッセージや PR 本文など書き換えられない場所にも残っていない場合に限り、別の意味で再利用してよい。参照が一つでも残るなら再利用しない
- **分割・統合**：元の識別子を参照する Relationship、本文中の言及、`//trace:checks` を、一括で同じ新しい識別子へ置換しない。参照元ごとに、新しいどの定義に依存すべきかを判断する

## 3. Relationships

Relationships は、記述元（Source）から参照先（Target）への意味を持つ直接関係です。文書間の単なる関連や言及とは区別します。

| Relationship | Source から Target への意味 |
|---|---|
| `alignment` | Source は、Target が定める要求・判断・定義・制約との整合を維持する |
| `grounding` | Target は、Source の重要な主張・判断・定義を支持する根拠である |
| `checks` | Source の検証手段は、Target が定める性質を検査対象とする |

Markdown では、関係を持つ定義またはセクションに、`Relationship`・`Target`・`Target Type` の3列からなるテーブルを直接置きます。次の例では「2.2 対象の同一性・認証・信頼境界」が Source、`FR-002` と GitHub リポジトリ API 仕様が Target です。

```markdown
### 2.2 対象の同一性・認証・信頼境界

（設計内容）

| Relationship | Target | Target Type |
|---|---|---|
| `alignment` | `FR-002` | Functional Requirement |
| `grounding` | [GitHub リポジトリ API 仕様](../research/repositories.md) | Internal Document |
```

テーブルは原則として Source となるセクションの末尾に配置します。下位見出しのある章全体を Source とする場合は、直前の小節に属するように見えないよう、最初の下位見出しより前の章本文に配置します。

Target には、専用の識別子、内部文書へのリンク、外部資料へのリンクのいずれかを書きます。識別子はコード表記（`FR-001` など）で書きます。内部文書と外部資料は `[タイトル](パス または URL)` 形式の Markdown リンクで書き、パスや URL だけを書きません。

- **内部文書へのリンク**：パスは Source の文書からの相対パスとし、リンクテキストには参照先の文書タイトルを使う
- **外部資料へのリンク**：URL には、根拠とする記述を特定できるよう、提供されていれば版やアンカーを含める。リンクテキストには参照先のページタイトルを使い、アンカーで節を指すときは「ページタイトル: 節見出し」とする。ページ自体が一つの操作や節に対応するとき（REST API の各エンドポイントなど）は、その見出しだけでよい

`Target Type`は Target が示す区分であり、次のように対応します。

| Target | Target Type |
|---|---|
| `FR-XXX` | Functional Requirement |
| `QR-XXX` | Quality Requirement |
| `INV-XXX` | Invariant |
| 内部文書へのリンク | Internal Document |
| 外部資料へのリンク | External Document |

Markdown の Relationship テーブルでは `alignment` と `grounding` を使用します。`checks` は Go のテスト関数に付ける `//trace:checks FR-001` のようなコメントで宣言し、Markdown テーブルには記述しません。

関係がなければテーブル自体を省略します。同一の Source・Relationship・Target を重複して記録せず、逆方向や推移的な関係も重複して定義しません。同じ話題を扱うだけでは関係を登録しません。

Relationships の存在は、要求の充足、根拠の正確性、検証の実施・合格・網羅性を保証しません。また、記録されていない依存関係が存在する可能性があります。

## 4. 参照と変更時の整合性

通常の文書参照には Markdown リンク `[タイトル](相対パス)` を使用します。本文中の Markdown リンクは参照先への移動を目的とし、Relationships は依存・根拠・検査対象の意味を記録するために使い分けます。Relationship テーブルの Target もリンク形式で書きますが、意味を持つのはテーブルに記録した関係であり、リンクは参照先へ移動するための手段です。

仕様や設計を変更するときは、次の点を確認します。

1. 変更する情報の正本を特定し、そこで変更内容を確定する。
2. 対象・条件・例外・期待結果など、変更前後の意味の差を確認する。
3. 識別子の同一性と、Relationships の参照先・意味を確認する。
4. 参照元や関連する要求・設計・契約・検証条件との整合性を確認する。記録されていない依存関係も必要に応じて調べる。

識別子やリンクが正しく解決できても、仕様同士の意味が整合するとは限りません。変更後も、関連する定義と検証条件が有効であることを確認します。

### 4.1 変更の種類と逆引きする参照元

参照元は、変更の種類ごとに次のように逆引きします。

| 変更 | 逆引きする参照元 | 確認すること |
|---|---|---|
| 表現の修正 | なし | 条件・範囲・例外の意味が変わっていないか |
| 見出しの変更・ファイルの移動 | 本文中のリンク、Relationship テーブルの Target、`llms.txt` | リンクが切れていないか。識別子は維持する |
| 機能要求・品質要求・不変条件の意味の変更 | その識別子を Target とする `alignment` を持つセクション、本文中の言及、その識別子を `//trace:checks` で宣言したテスト、ユーザーガイドの文書のうち References に要求定義を挙げるものか、その識別子に言及するもの | 参照元が変更後の条件と整合するか。テストの検査条件と期待結果が変更後の意味に合うか |
| CLI 仕様・YAML 設定仕様の変更 | その文書を参照する設計の節、関係するテスト、References にその文書を挙げるユーザーガイドの文書 | 設計と実装が変更後の契約を前提にしているか。ガイドの説明と出力例が変更後の契約と食い違わないか |
| 用語集が要約する用語の意味の変更 | 用語集、その用語を使うユーザーガイドの文書 | 用語集の言い換えとガイドの説明が、変更後の意味を保っているか |
| GitHub API 仕様の変更 | 変更した GitHub API 仕様の文書を Target とする `grounding` を持つすべてのセクション | 主張が引き続き根拠に支持されるか |

`grounding` の Target はファイル単位で書くため、GitHub API 仕様の変更では、変更した節に依存しない箇所も逆引きの候補に含まれます。本文中に `[GitHub リポジトリ API 仕様](../research/repositories.md) 4章` のような節番号を添えたリンクがあれば、変更した節に依存する箇所を先に特定する手がかりになります。ただし、節番号を添えずに依存している箇所もあるため、節番号のない候補も、主張が変更した節に依存していないかを確認します。

テストが合格しても、検査条件が変更後の意味に合っているとは限りません。テストは変更前の意味を前提に書かれており、意味を変えた後も合格し続けることがあるためです。`//trace:checks` で宣言したテストは、合格していても期待結果を読み直します。

### 4.2 新しく見つかった制約の正本

実装、GitHub API の実際の動作の確認、テストの失敗などで新しい制約が見つかった場合は、見つけた場所に規範を書き足しません。見つけた場所に書くと、正本の外に正本と食い違い得る規範が生まれるためです。要求定義・CLI 仕様・YAML 設定仕様・GitHub API 仕様のうち、その制約に責務を持つ正本で採否を決めてから、参照元を合わせます。

### 4.3 確認の深さ

変更が安全性の保証にどれだけ関わるかによって、確認の深さを変えます。

| 深さ | 対象 | 確認の中心 |
|---|---|---|
| 重点 | 不変条件全般、`QR-001`、HTTP リダイレクトの扱い、更新操作の結果判定（[アーキテクチャ設計](../design/architecture.md) 6.1 の表）、未管理設定の保全（[アーキテクチャ設計](../design/architecture.md) 5.3） | 条件を緩めていないかの差分確認、失敗シナリオ、根拠との照合。条件を緩める変更は人間が判断する |
| 標準 | 重点以外の機能要求・品質要求、CLI 仕様、YAML 設定仕様 | 4.1 の逆引き、境界例と例外 |
| 軽量 | 表現の修正、見出しの変更、ファイルの移動 | リンクと構造 |

重点の対象は、条件を緩めてもテストが失敗するとは限らず、緩めた結果が誤った更新や認証情報の漏えいとして現れる定義です。

## 5. ユーザーガイド

ユーザーガイド（`docs/user-guide/`）は、reco を使う人が目的に沿って読む文書です。ガイドは正本の事実を利用者の目的の順に並べて説明し、正本の構成と書き方はガイドのために変えません。

### 5.1 位置づけ

ガイドは正本（要求定義、CLI 仕様、YAML 設定仕様、設計文書、GitHub API 仕様）の説明であり、新しい規則を書きません。ガイドと正本が食い違えば正本が優先し、ガイドのほうを直します。ガイドを書く途中で正本の誤り、正本どうしの食い違い、正本にない制約を見つけた場合は、ガイドに規則を書き足さず、4.2節に従って正本で採否を決めます。

ガイドの本文には、ガイドの外へのリンクを置きません。読者は目的の情報だけを少ない量で得たいのに、本文の途中で仕様へ誘導されると、それも読むべきかで迷うためです。ガイドが説明している正本と、ガイドの外の参照先（Issue など）は、各文書の末尾の References に集め、項目ごとにそこで確かめられることを一言添えます。ガイドの文書どうしのリンクは本文に置いてかまいません。

ガイドのセクションには Relationship テーブルを置きません。ガイドのセクションは定義ではなく説明であり、Relationship テーブルで記録する関係（`alignment`、`grounding`）を持たないためです。正本を変えるときの逆引き（4.1節）は、References と識別子への言及を手がかりにします。References は正本を文書単位で挙げるため、逆引きで特定できるのはガイドの文書までです。ガイドの文書は短く、文書ごとに読み直す負担が小さいため、この粗さを受け入れます。

ガイドは `docs/` 配下のほかの文書と同じく日本語で書き、英語版は作りません。

### 5.2 用語

ガイドの用語は、[用語集](../user-guide/glossary.md) の語と言い換えを使います。同じ概念を文書ごとに別の語で言い換えると、出力や正本の語と結び付かなくなるためです。

用語集は、ドメインモデルや要求定義の用語を、意味を変えずに要約したものです（1章）。言い換えは一文にとどめ、用語が使われる条件や例外を書きません。条件を書くと用語集が規則を定めることになり、正本と食い違い得る箇所が増えるためです。用語集にない用語が要るときは、先に用語集に足してから使います。

### 5.3 文書の依存

ガイドの文書のあいだの内容の依存（ある文書が、ほかの文書で決めた用語、概念、責務の境界を前提に書かれること）は一方向とします。前提にされる側の文書は、それを前提にする側の文書の内容を前提にした説明を書きません。案内のためのリンクは双方向に置いてよく、前提にされる側から前提にする側へのリンクは、前提にする側の文書を足すときに足します。依存をリンクの有無で判断しないのは、文書どうしが案内のために互いにリンクし合い、リンクで見ると循環が残るためです。

| 文書 | その文書が前提とする文書 |
|---|---|
| [reco ユーザーガイド](../user-guide/README.md) | 正本だけ |
| [用語集](../user-guide/glossary.md) | 正本だけ |
| [設定ファイルの書き方](../user-guide/configuration.md) | 用語集 |
| [reco の安全性の約束](../user-guide/safety.md) | 用語集、設定ファイルの書き方 |
| [コマンドリファレンス](../user-guide/commands.md) | 用語集、設定ファイルの書き方、reco の安全性の約束 |
| [変更計画と変更結果の読み方](../user-guide/reading-output.md) | 用語集、設定ファイルの書き方、reco の安全性の約束、コマンドリファレンス |

### 5.4 責務の境界

内容が重なりやすい文書の組について、どちらに何を書くかを次の表で定めます。同じ事実を二か所に書くと、片方だけを直したときに食い違うためです。文書を足して重なる組が生まれたら、行を足します。

| 文書の組 | どちらに何を書くか |
|---|---|
| 用語集と、ほかのガイドの文書 | 用語の言い換えと、出力のどこに現れるかは用語集に書く。用語が使われる条件と例外は、ほかの文書が書く |
| 設定ファイルの書き方と、reco の安全性の約束 | 何を書けば何が管理されるか、設定ごとに GitHub 側で起きることは設定ファイルの書き方に書く。reco がそれをどう守り、何を守らないかは安全性の約束に書く |
| reco の安全性の約束と、コマンドリファレンス | reco が何を保証するか、止まる場面とその理由は安全性の約束に書く。承認の入力、承認を求めない場面、更新の順序・所要時間・中断、終了コードの意味はコマンドリファレンスに書き、止まる場面は安全性の約束へリンクする |
| 設定ファイルの書き方と、コマンドリファレンス | 設定ファイルに何をどう書くか、書き方の誤りとそのエラーの例は設定ファイルの書き方に書く。オプションとその既定値、出力先とエラーの形式はコマンドリファレンスに書く |
| コマンドリファレンスと、変更計画と変更結果の読み方 | コマンドが何をし、いつ止まるかはコマンドリファレンスに書く。出力の各行が何を意味するかは変更計画と変更結果の読み方に書く |
| reco の安全性の約束と、変更計画と変更結果の読み方 | reco が止まる場面とその理由、完了とする条件は安全性の約束に書く。止まったことや完了しなかったことを示す行の意味は変更計画と変更結果の読み方に書き、理由は安全性の約束へリンクする |
| 設定ファイルの書き方と、変更計画と変更結果の読み方 | 設定ごとに GitHub 側で起きること（副作用で消える値を含む）は設定ファイルの書き方に書く。それが変更計画のどの行にどう示されるかは変更計画と変更結果の読み方に書く |

### 5.5 文書を足すか変えるときの確認

ガイドの文書を足すか変えるときは、既存のガイドの全文書について次の点を確かめ、既存の文書を直す必要があれば同じ変更で直します。一つの文書だけを見て足すと、用語の揺れや重複が文書のあいだに生まれても気付けないためです。

- 用語集の語と言い換えを使っているか
- 同じ事実を二か所に書いていないか
- 責務の境界（5.4節）を守っているか
- 記述が互いに食い違っていないか
- 本文にガイドの外へのリンクがなく、説明している正本が References にあるか
- 読者の行動か判断を変えない記述がないか（5.7節）

文書を足したときは、5.3節の表、ガイドの README の文書一覧と「目的から選ぶ」の該当行のリンク、`llms.txt` にも足します。

### 5.6 出力例と未確認の事項

ガイドに載せる `show`、`plan`、`apply` の出力例は、CLI 仕様の表示例を使い、`make build` した実行ファイルの出力と食い違わないことを確かめます。CLI 仕様は表示例の空白・改行・エラーメッセージの完全一致を契約としていないため（[CLI 仕様](../spec/cli.md) 7章）、これらが実際の出力と違う箇所は、実際の出力に合わせて示します。それ以外の違いは正本と実装の食い違いであり、4.2節に従って正本で採否を決めます。

CLI 仕様に定めがあっても、現在の reco が出力する経路のない出力は書きません。読者が出会わない出力を説明すると、読者は自分の出力にその行がないことを異常と読み違えるためです。

reco で動作を確かめていない条件（CLI 仕様 3章が確認していないとするロールなど）は、確かめていないと書きます。設定と GitHub の設定画面の項目の対応を示すときは、GitHub の公式資料で項目名を確かめ、確かめられなければ書きません。

### 5.7 読者と分量

ガイドの読者は、GitHub の個人アカウントで複数のリポジトリを持ち、設定画面の項目をある程度知っている人です。Go や GitHub REST API の知識は前提にしません。読者は文書を通読せず、いま抱えている問い（自分に使えるか、どう書くか、この行は何か、止まったらどうするか）の答えだけを探します。正確でも量の多い文書は、答えを探す手間を増やし、読まれなくなります。

そのため、ガイドには読者の行動か判断を変える事実だけを書きます。正本は開発者が条件を確定するために全条件を書いており、正本と同じ密度で書くと、この基準を満たさない記述が大半を占めます。

- 各セクションは、読者の問い一つに答える
- 多くの読者が出会わない条件、例外、境界（入力検証の細則、内部の仕組み、待ち時間の決め方など）は書かず、References の正本に任せる
- 同じ種類の例は一つに絞る
- 正本の条件を省くときは、省いた結果、約束が実際より広く読めないようにする。条件をすべて書けない約束は、確かに成り立つ範囲だけを書く

誤った記述を書かないことは、分量を減らすかどうかにかかわらず守ります（5.1節、5.6節）。分量を減らすのは、読者に要らない事実を書かないことによってであり、事実を不正確に丸めることによってではありません。
