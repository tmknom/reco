# ドキュメント規約

本ドキュメントは、reco リポジトリの文書を読み、変更するための共通規約を定めます。文書が規定する情報の責務、識別子、Relationships、変更時の参照方法、ユーザーガイドの書き方を対象とします。

## 1. 文書の責務と正本

正本とは、ある情報の意味を確定・変更するときに優先する定義です。文書の詳しさや作成順序ではなく、規定する内容によって正本を区別します。

| 文書 | 主な責務 |
|---|---|
| Constitution | reco の存在理由、解決する問題、提供価値、設計判断の原則 |
| 要求定義 | 提供する機能、必要な振る舞い、品質、保証、適用範囲 |
| CLI 仕様 | コマンド、オプション、認証情報の選択、承認の入力、出力先、エラーの形、終了コードなどの、操作の外部契約 |
| 表示仕様 | `plan`・`apply`・`show` の表示の構造、固定の語、各行が伝える情報、並びと数え方などの、表示の外部契約 |
| YAML 設定仕様 | 設定宣言の構造、型、許容値、入力検証などの外部契約 |
| ドメインモデル | リポジトリ設定の管理に関する、どの設定にも通じる概念の意味と区別 |
| アーキテクチャ設計 | システムの論理構成、責務、依存関係、計画から実行までの情報の流れ、すべての設定が従う仕組みの原則 |
| GitHub API 通信の設計 | すべての設定に共通する、GitHub への要求と応答の解釈の細則（取得契約、リポジトリの読み取り、関連リソースの一覧の読み方、関連リソースの名前を含む宛先、更新操作の結果の判定、読み取りの再試行） |
| 変更の実行の設計 | すべての設定に共通する、承認後の観測し直しと更新要求の間隔の細則 |
| 設定ごとの設計 | 設定宣言のトップレベルのキーごとの、設定の観測、適用可能性と副作用、論理的な設定変更と更新操作、更新方式。`docs/design/settings/` の複数の文書からなる |
| GitHub API 仕様 | reco が利用する GitHub REST API の外部契約を、GitHub の公式資料から抜粋・整理したもの。`docs/research/` の複数の文書からなる |
| ユーザーガイド | 利用者の目的に沿った、正本の説明。`docs/user-guide/` の複数の文書からなる。規則の正本ではない（5章） |

文書は、読者によって二つに分かれます。`docs/user-guide/` のユーザーガイドは、reco の利用者（reco を実装しない人）が読みます。それ以外の `docs/` 配下の文書（Constitution、仕様、設計、GitHub API 仕様、この規約を含む開発者向けの文書）は、reco の実装者が読みます。実装者向けの文書は条件を確定するために全条件と術語を書き、ユーザーガイドは利用者が少ない労力で使えるように書くため、書き方の規則が違います。この章から4章までの規則は実装者向けの文書のためのもので、ユーザーガイドの書き方は5章が定めます。

用語の意味は、ドメインモデルを正本とします。ほかの文書で用語を導入するときは、意味を変えずに要約します。

設計の文書は、変わる契機で分けます。ドメインモデルとアーキテクチャ設計（その細則を定める GitHub API 通信の設計と変更の実行の設計を含む）は、新しい概念か処理の仕組みを足すときに変わる文書であり、扱う設定を足しても変わらないように書きます。特定の設定についての設計（どの読み取り要求で読み、応答をどう解釈し、どの変更予定が適用可能で、どの順にどう更新するか）は、その設定が属する [設定ごとの設計](../design/settings/README.md) に書きます。ドメインモデルとアーキテクチャ設計が特定の設定に触れるのは、一般の規則の例として名前を挙げるときだけで、その設定に固有の規則は書きません。二つの文書にまとめて置くと、設定を一つ足すたびに、概念や仕組みの記述のあいだに固有の規則が書き足され、変わらないはずの記述まで読み直すことになるためです。設定ごとの設計は、一般の規則をドメインモデルとアーキテクチャ設計から参照し、繰り返しません。

ドメインモデルには、どの設定にも通じる概念の意味と、取り違えると誤った判断になる概念どうしの区別だけを書きます。ドメインモデルは、ほかの設計文書と仕様が語の意味を確かめる正本です。設定ごとの事実や処理の細則を置くと、設定を足すか仕組みを変えるたびに書き換えが起き、どれが概念の定義でどれが一つの設定の事情かを読み分けられなくなるためです。ドメインモデルに書くことは次のとおりです。

- **概念と区別**：用語の定義、概念どうしの関係、似た概念の区別（観測不能と観測操作の失敗、更新操作の結果と変更結果など）、区別を誤ったときに起きること
- **概念の内訳と判定の基準**：照合結果、変更前提の不成立の形、関係する現在値に当たる設定の種類のように、どの設定にも同じ基準で当てはまる内訳
- **文脈**：概念がどの文脈に属し、どの語を文脈が共有するか
- **シナリオと反例**：一般の概念の意味を確かめる例。設定の名前は、一般の規則の例として挙げてよい

次のことはドメインモデルに書かず、それぞれの正本に書きます。

- **特定の設定の事実と規則**：どの設定がどの取得条件で観測不能になるか、どの変更予定がどの副作用を伴うか、どの更新操作が何を関係する現在値にするか。設定ごとの設計に書く。用語表と本文では、設定の名前を括弧の中の例として挙げるだけにする。その設定の事実がなければ成り立たないシナリオは、設定ごとの設計の「シナリオと反例」に書く
- **処理の仕組み**：何を読み、どの順に要求し、どれだけ待つか、応答のどの形をどう判定するか。アーキテクチャ設計とその細則の文書に書き、ドメインモデルは概念の意味（観測の時点、観測し直しが一つの時点の中で行われることなど）だけを書く
- **宣言と表示の形**：キー、許容値、表示の行と語。YAML 設定仕様と表示仕様に書く
- **GitHub API の事実**：GitHub API 仕様に書く

用語表（3章）は定義だけを書き、内訳や例は4章の節に書きます。用語表と4章の両方に同じ説明を書くと、片方だけを直して食い違うためです。4章の節の見出しは、ほかの文書と Go のコメントが名前で参照するため、変えるときは参照元も直します（4.1節）。

アーキテクチャ設計には、実装が変わっても残る、reco 全体の構造と、すべての設定が従う仕組みの原則だけを書きます。アーキテクチャ設計は、領域か仕組みを足すときに読み直す文書です。細則や個別の事実を置くと、原則が変わっていないのに書き換えが起き、どれが全体に効く判断かを読み取りにくくなるためです。アーキテクチャ設計に書くことは次のとおりです。

- **論理構成と責務**：領域、各領域の責務と境界、依存と呼び出しの向き、package の分け方とその理由
- **情報の流れ**：宣言から観測、照合、適用可能性、変更計画、承認、実行、結果までを、どの領域が担うか
- **信頼境界と安全の原則**：対象の同一性、認証情報の扱い、リダイレクト、未管理設定の保全、非原子的な更新、後続の更新を止める条件、更新要求を再送しないこと。条件と、その条件を選んだ理由を書く
- **細則の置き場所**：原則に従う細則を定める文書への参照

次のことはアーキテクチャ設計に書かず、それぞれの正本に書きます。

- **概念の意味と区別**：ドメインモデルに書く。照合結果、変更結果、変更前提、副作用、関連リソースの存在のような語の内訳や、何が関係する現在値に当たるかを繰り返さない
- **すべての設定に共通する仕組みの細則**：GitHub への要求と応答の解釈（取得契約、一覧の読み方、応答から更新操作の結果を決める表、読み取りの再試行）は GitHub API 通信の設計に、承認後の観測し直しの条件・間隔・回数と更新要求の間隔は変更の実行の設計に書く。アーキテクチャ設計には、細則が守る原則（成功応答だけで値を確認したとしない、`4xx` だけを失敗とする、観測し直しは止める条件を減らさないなど）だけを書く
- **特定の設定の規則と GitHub の個別の挙動**：設定ごとの設計と GitHub API 仕様に書く。特定のエンドポイント、フィールド、設定に触れるのは、一般の規則の例として名前を挙げるときだけにする
- **操作・表示・宣言の契約**：CLI 仕様、表示仕様、YAML 設定仕様に書く
- **コードを読めば分かること**：個々の型をどの package に置くか、関数の分け方、値を並べる順のように、コードから読み取れる配置は書かない。理由がコードから読み取れない判断は、全体に効くならアーキテクチャ設計に、一か所に閉じるならそのコードのコメントに書く

GitHub API 通信の設計と変更の実行の設計は、アーキテクチャ設計の GitHub Access と Change Execution が従う細則を定めます。原則を変えずに細則だけを変えるときは、この二つの文書だけを直します。細則の変更が原則を変える（後続の更新を止める条件を減らす、成功とみなす応答を広げるなど）ときは、先にアーキテクチャ設計で原則の採否を決めます。二つの文書は、特定の設定の値や応答の形を扱わず、設定ごとの設計を参照します。

設定ごとの設計には、一つのトップレベルのキーの設定に固有で、実装が変わっても残る判断と、その根拠だけを書きます。設定ごとの設計は、その設定の扱いを変えるときに読み直す文書です。一般の規則の言い直しやコードの説明を置くと、一般の規則を変えるたびに設定の数だけ直す箇所が増え、どれがその設定に固有の判断かを読み取りにくくなるためです。設定ごとの設計に書くことは次のとおりです。

- **GitHub の事実への依拠**：その設定を読む読み取り要求と送る条件、取得契約のフィールド、取得条件、GitHub の応答の解釈（失敗の応答を値として読む条件など）
- **設定に固有の判断と理由**：適用不能の条件、変更に伴う副作用と再開する設定、論理的な設定変更へのまとめ方と順序、関係する現在値、送るフィールドと未管理設定を保全する根拠。採らなかった案があれば、採らなかった理由
- **表示で示す、設定に固有の情報**：表示仕様の一般の規則を当てはめるだけでは決まらない、その設定の行が示す情報（適用不能の理由と直し方、副作用で示す設定、原因の候補、`show` で値の全体をコメントにする範囲など）と、その理由。文言は書かない（この章の、CLI 仕様と表示仕様の段落）
- **確かめていない条件**：判断が依拠しているが、公式資料にも実際の動作の確認にも裏付けのない GitHub の挙動
- **導いた値の導出**：上限などの値を GitHub の制限から導いたときの計算と代償。値はコードにあっても、導出はコードから読み取れないため
- **固有の事実がなければ誤る例**：シナリオと反例

次のことは設定ごとの設計に書かず、それぞれの正本に書きます。

- **一般の規則の言い直し**：ドメインモデル、アーキテクチャ設計、GitHub API 通信の設計、変更の実行の設計の規則を、その設定に当てはめただけの文（関連リソースの照合表、作成と削除の変更前提と期待状態、属する先が存在しないときの扱い、取得条件に当たらないと観測した直後の拒否の扱い、`4xx` を失敗とする判定など）。設定の事実がどの場合に当たるかだけを書き、規則は参照する。一般の規則を当てはめただけのシナリオも書かない
- **設定を問わない仕組み**：リポジトリの読み取りの取得契約、関連リソースの名前をパスに入れる規則のように、設定によらない規則。GitHub API 通信の設計か変更の実行の設計に書く。二つ以上の設定ごとの設計に同じ規則が現れたら、一般の規則として正本に移せないかを先に確かめる
- **コードを読めば分かること**：関数の分け方、送る本文の JSON の例、判断を含まないフィールドの対応。同じ内容を要約の表と本文で二度書くことも、片方だけを直して食い違うため避ける
- **宣言と表示の形**：入力検証で拒否する組み合わせ、変更予定の集計、行の形。YAML 設定仕様と表示仕様に書き、設定ごとの設計は、ある場合が生じない理由として参照するだけにする
- **表示の文言**：理由文、注記、原因の候補の英文。コードとテストに書く（この章の、CLI 仕様と表示仕様の段落）
- **経緯**：以前の案や検討の順序。採った判断の理由だけを書く
- **ほかのキーの設定の規則**：キーをまたぐ依存は、それぞれの文書が自分の更新操作について書き、もう一方の設定の規則は参照する

要求定義には、実装や設計が変わっても残る、reco が利用者に約束する振る舞いと保証だけを書きます。要求定義の意味を変えると、その識別子を参照する設計の節とテストをすべて確かめ直すことになります（4.1節）。設計や外部契約の詳細を要求定義に置くと、それらを変えるたびに要求定義も変わり、要求が変わっていないのに確かめ直しが起きるためです。要求定義に書くことは次のとおりです。

- **目的と対象範囲**：対象とする GitHub とリポジトリ、サポートする設定と関連リソースへの操作の一覧、サポート対象外。対象範囲は、機能要求と不変条件を読むための前提にとどめる
- **機能要求・品質要求・不変条件**：利用者から観察できる振る舞いと保証。条件は利用者から見た事実（観測できたか、更新を始めたか、承認を得たかなど）で書く
- **用語の要約**：要求を読むのに要る用語だけを、ドメインモデルの意味を変えずに要約する

次のことは要求定義に書かず、それぞれの正本に書きます。

- **用語の定義と内訳**：ドメインモデルに書く。観測不能の理由の列挙のような、用語の内訳を要求定義で繰り返さない
- **宣言の形と読み方**：YAML 設定仕様に書く。キー、許容値、一覧を値とする設定の読み方など
- **コマンド、表示、終了コード**：操作と終了コードは CLI 仕様に、表示は表示仕様に書く
- **仕組みと設定ごとの規則**：アーキテクチャ設計とその細則の文書、設定ごとの設計に書く。処理の順序、使う読み取り要求と更新要求、特定の設定の適用可能性など。サポート対象の表は、設定を名前で挙げるだけにする
- **GitHub API の事実**：GitHub API 仕様に書く。HTTP の応答の扱いを要求定義に書くのは、利用者への保証を左右する場合（リダイレクトに追従しないことなど）に限る

要求定義の中でも、同じ規則を対象範囲と機能要求・不変条件の両方に書きません。二か所に書くと、片方だけを直して食い違うためです。振る舞いの条件は機能要求か不変条件の一か所に置き、対象範囲では繰り返しません。

CLI 仕様と表示仕様は、どちらも利用者から見える外部契約を定めます。CLI 仕様は、利用者が reco を操作し、結果を機械的に受け取るための契約を、表示仕様は、利用者が `plan`・`apply`・`show` の表示を読んで判断するための契約を定めます。二つに分けるのは、変わる契機が違うためです。操作の契約はコマンドかオプションを足すときに変わり、表示の契約は表示の仕組み（新しい種類の行など）を足すときに変わります。どちらも、扱う設定を足しても変わらないように書きます。設定ごとの判断を置くと、設定の設計を変えるたびに仕様も変わり、一つの規則を二つの文書で直すことになるためです。表示仕様が表示の形と伝える情報を決め、設定ごとの設計がその表示をいつ出し、その設定について何を示すかを決めます。

外部契約にするのは、破ると利用者の判断か安全か、reco を呼ぶスクリプトが損なわれる事柄だけです。表示の文言（理由文、注記、原因の候補など）と値の細かい表記（単位の書き方、字下げ、項目の並びなど）は外部契約にせず、コードとテストを正本とします。文言を外部契約にすると、利用者の判断を変えない言い換えのたびに仕様が変わり、仕様が実装を後から書き写すだけの記録になるためです。文言が伝えなければならない情報は、外部契約として表示仕様と設定ごとの設計に書きます。

CLI 仕様に書くことは次のとおりです。

- **操作**：コマンド、オプション、対象の選び方、認証情報の選び方、対話承認の受け付け方
- **結果の受け渡し**：stdout と stderr の分け方、エラーの形、終了コード

表示仕様に書くことは次のとおりです。

- **表示の構造**：`plan`・`apply`・`show` の節と行の種類、行の並びと数え方
- **固定の語**：行のラベル（`Applicability:`、`Side effect:` など）、結果区分（`updated`、`failed` など）、`absent` と `present`、`No changes.` のような全体の結論を示す行。利用者とユーザーガイドが行を見分けるのに使うため、外部契約にする
- **行が伝える情報**：各行が示さなければならない情報と、示してはならない情報
- **表示例**：形を示すための少数の例。例の文言と細かい表記は外部契約ではない

次のことは CLI 仕様と表示仕様に書かず、それぞれの正本に書きます。

- **設定ごとの判断**：どの変更予定が適用不能になるか、どの副作用や再開する設定を伴うか、変更予定のまとめ方と実行順、変更前提で何を比べるか、原因の候補は何か、どの設定がどの理由で観測不能になるか。設定ごとの設計に書き、表示仕様はその行の形と伝える情報だけを定めて参照する
- **文言と細かい表記**：コードとテストに書く。設定ごとの値の表記（担当者や個別パターンの書き方など）も、一般の規則から外れる判断がない限り書かない
- **仕組み**：更新要求の間隔、観測し直しの回数と時間、要求を送る範囲と順序。変更の実行の設計と GitHub API 通信の設計に書く。利用者から見える影響（時間がかかること、中断で次の更新を始めないこと）だけを CLI 仕様に書く
- **GitHub API の挙動**：どの要求にどの権限が要るか、どの応答を返すか。GitHub API 仕様に書く。CLI 仕様と表示仕様には、reco がその応答を利用者にどう示すかだけを書く
- **要求の言い換え**：適用範囲や不変条件の繰り返し。要求定義を参照する

YAML 設定仕様には、設定ファイルに何をどう書けるか、書いたものが何を意味するかという外部契約だけを書きます。判断の基準は、宣言だけから決まるかどうかです。入力検証は設定ファイルだけを読んで行い、GitHub を観測しないため、観測のあとに決まる判断を YAML 設定仕様に置くと、入力検証で確かめられる規則と確かめられない規則が同じ文書に混ざり、どちらがエラーになるかを読み違えるためです。YAML 設定仕様に書くことは次のとおりです。

- **構造と型**：キーの階層、型、必須と省略、許容値
- **宣言の意味**：期待値として何を求めるか（`false` や空集合、存在しないことの宣言、一覧の全体を値とする設定、ほかの設定の状態を期待値に含むか）、設定グループ、名前の同一性の規則
- **入力検証**：拒否する入力、設定どうしの組み合わせ、誤りを示す順と直し方
- **規則の理由**：宣言で受け付けない値や組み合わせを決めた理由。GitHub の事実を理由にするときは GitHub API 仕様を参照する

次のことは YAML 設定仕様に書かず、それぞれの正本に書きます。

- **観測のあとに決まる判断**：リポジトリの状態によってどの宣言が適用不能になるか、どの副作用を伴うか。設定ごとの設計の「適用可能性と副作用」に書く。YAML 設定仕様は、入力として有効な宣言でも適用不能になり得ることを一般の規則として示し、設定ごとに繰り返さない
- **観測値の扱い**：GitHub から取得した値の比べ方（重複の扱いなど）と、宣言の名前と GitHub 上の名前の突き合わせ。設定ごとの設計の「観測」と「設定と管理の単位」に書く
- **計画と実行**：変更予定の表示順、実行順、更新の分け方、更新後に確かめること。表示仕様と設定ごとの設計に書く
- **GitHub API の挙動の説明**：GitHub API 仕様に書く。宣言の規則の理由として要る範囲だけを参照する

キー名、値、階層をどう決めるか、GitHub REST API の名前と異なる名前がどこから来たかは、[設定ファイルのインターフェイス設計方針](configuration-policy.md) が定めます。YAML 設定仕様は、決めたキーと値を書き、名前の由来を繰り返しません。

GitHub API の契約は GitHub の公式資料が正本です。開発のたびに公式資料を参照しなくて済むよう、必要な事実は [GitHub API 仕様](../research/README.md) に抽出します。GitHub API 仕様を構成する文書と、事実をどの文書に書くかは、GitHub API 仕様の README が定めます。GitHub API 仕様は GitHub の公式資料だけを根拠とし、ほかの内部文書に依存せず単独で読めるようにします。ただし、公式資料の記載が不十分で、reco の開発者が実際の動作を確認した事項は、公式資料の記載と区別できる注釈として記載できます。依存の向きは一方向であり、ほかの内部文書が GitHub API の事実を根拠とするときは GitHub API 仕様を参照し、GitHub API 仕様からほかの内部文書は参照しません。スクリプトは文書ではないため内部文書に含まず、GitHub API 仕様から参照できます。GitHub API 仕様に必要な事実がなければ、公式資料で確認して GitHub API 仕様に追記してから参照します。

reco の要求・契約・設計における独自の判断と、GitHub が定めた事実を区別します。GitHub の事実をどう扱うかは参照する側の文書で定め、GitHub API 仕様には書きません。同じ規則を複数文書で独立して定義せず、必要な箇所から正本を参照します。

要求・契約・設計は、推測で決めません。公式資料にも reco の動作の確認にも裏付けのない条件（CLI 仕様 3章の Write・Maintain ロールなど）は、確かめていないと書き、確かめた条件と区別します。確かめていない条件を確かめたものとして扱うと、その上に置いた設計や保証が根拠を失うためです。この規則は実装者向けの文書のためのものであり、ユーザーガイドには適用しません。

## 2. 識別子

要求や不変条件などの定義を安定して参照するため、次の識別子を使います。

| 形式 | 対象 |
|---|---|
| `FR-001` | 機能要求：提供する能力、振る舞い、重要な操作上の保証 |
| `QR-001` | 品質要求：検証可能な品質上の性質・制約 |
| `INV-001` | 不変条件：適用範囲内で維持すべき状態・遷移の性質 |

識別子は定義見出しの先頭に置きます。プレフィックスごとに3桁以上の連番を使い、識別対象とした情報種別では重要度にかかわらず全定義に付与します。説明や具体例には、独立した定義でない限り新しい識別子を付けません。

要求定義の「機能要求」「品質要求」「不変条件」の各章では、直下の見出しをすべて識別子付きの定義見出しとします。分類のための見出しを同じ階層に置きません。

この3章の見出しのテキストは、リポジトリ直下の `sdlc.yaml` が定義の置き場所として参照します（4.4節）。そのため、要求定義の見出しには章番号・節番号を付けません。番号を付けると、章を足すか並べ替えて番号がずれるだけで参照が外れ、`sdlc.yaml` も直さなければならなくなるためです。ほかの文書から要求定義の章を指すときは、番号ではなく見出しのテキスト（要求定義の「対象範囲」など）で指します。この3章の見出しを変えるときは、同じ変更で `sdlc.yaml` も直します。

識別子が表すのは定義の同一性であり、ファイルの位置や検証状況ではありません。定義の責務が継続するなら、見出しや配置が変わっても識別子を維持します。意味を変更した場合は、識別子を維持しても参照元を再確認します。識別子を変更する場合は、リポジトリ全体に変更を反映し、一貫性が保たれるようにします。

定義を削除・分割・統合するときは、次の規則に従います。

- **削除した識別子の再利用**：削除前の意味への参照が、リポジトリ内にも、コミットメッセージや PR 本文など書き換えられない場所にも残っていない場合に限り、別の意味で再利用してよい。参照が一つでも残るなら再利用しない
- **分割・統合**：元の識別子を参照する Relationship、本文中の言及、`//trace:checks` を、一括で同じ新しい識別子へ置換しない。参照元ごとに、新しいどの定義に依存すべきかを判断する

## 3. Relationships

Relationships は、記述元（Source）から参照先（Target）への意味を持つ直接関係です。文書間の単なる関連や言及とは区別します。

- **`alignment`**：Source は、Target が定める要求・判断・定義・制約との整合を維持する
- **`grounding`**：Target は、Source の重要な主張・判断・定義を支持する根拠である
- **`checks`**：Source の検証手段は、Target が定める性質を検査対象とする

この種類の説明は、表ではなく箇条書きで書きます。第1列が `alignment` などの種類だけの表は、Relationship テーブルとして検査され、列の構成が違うため違反になるためです（4.4節）。

Markdown では、関係を持つ定義またはセクションに、`Relationship`・`Target`・`Target Type` の3列からなるテーブルを直接置きます。次の例では「2.2 対象の同一性・認証・信頼境界」が Source、`FR-002` と GitHub リポジトリ API 仕様が Target です。

```markdown
### 2.2 対象の同一性・認証・信頼境界

（設計内容）

| Relationship | Target | Target Type |
|---|---|---|
| `alignment` | `FR-002` | Functional Requirement |
| `grounding` | [GitHub リポジトリ API 仕様](../research/repositories.md) | Repository File |
```

テーブルは原則として Source となるセクションの末尾に配置します。下位見出しのある章全体を Source とする場合は、直前の小節に属するように見えないよう、最初の下位見出しより前の章本文に配置します。

Target には、専用の識別子、リポジトリ内のファイルへのリンク、外部資料へのリンクのいずれかを書きます。識別子はコード表記（`FR-001` など）で書きます。識別子を持つ定義は、リンクのアンカーではなく識別子で指します。アンカーは見出しから作られるため、見出しを変えると切れるためです。リポジトリ内のファイルと外部資料は `[タイトル](パス または URL)` 形式の Markdown リンクで書き、パスや URL だけを書きません。

- **リポジトリ内のファイルへのリンク**：内部文書とスクリプトへのリンクである。パスは Source の文書からの相対パスとし、リンクテキストには参照先の文書タイトルを使う
- **外部資料へのリンク**：URL には、根拠とする記述を特定できるよう、提供されていれば版やアンカーを含める。リンクテキストには参照先のページタイトルを使い、アンカーで節を指すときは「ページタイトル: 節見出し」とする。ページ自体が一つの操作や節に対応するとき（REST API の各エンドポイントなど）は、その見出しだけでよい

`Target Type`は Target が示す区分であり、次のように対応します。

| Target | Target Type |
|---|---|
| `FR-XXX` | Functional Requirement |
| `QR-XXX` | Quality Requirement |
| `INV-XXX` | Invariant |
| リポジトリ内のファイルへのリンク | Repository File |
| 外部資料へのリンク | External Document |

Markdown の Relationship テーブルでは `alignment` と `grounding` を使用します。`checks` は Go のテスト関数の直前のコメントで宣言し、Markdown テーブルには記述しません。

```go
//trace:checks FR-008 FR-002
func TestApply_NoChanges(t *testing.T) {
```

- **1関数に1行**：一つのテスト関数の宣言は1行にまとめ、識別子を半角スペースで区切る。並び順は意味を持たない。2行目以降の宣言は違反になり、Relationship として数えられない
- **書式**：`//` と `trace:checks` のあいだに空白を置かない。`// trace:checks` は違反になる
- **付ける場所**：トップレベルのテスト関数の直前に、空行を挟まずに置く。`t.Run` のサブテストには付けない。サブテストの一部だけが検査する性質は、そのケースを独立したテスト関数に切り出して宣言する。親のテスト関数の宣言に足すと、親の全体がその識別子の再検証候補になり、宣言が意図した範囲より広がるためである

関係がなければテーブル自体を省略します。同一の Source・Relationship・Target を重複して記録せず、逆方向や推移的な関係も重複して定義しません。同じ話題を扱うだけでは関係を登録しません。

Relationships の存在は、要求の充足、根拠の正確性、検証の実施・合格・網羅性を保証しません。また、記録されていない依存関係が存在する可能性があります。

## 4. 参照と変更時の整合性

通常の文書参照には Markdown リンク `[タイトル](相対パス)` を使用します。本文中の Markdown リンクは参照先への移動を目的とし、Relationships は依存・根拠・検査対象の意味を記録するために使い分けます。Relationship テーブルの Target もリンク形式で書きますが、意味を持つのはテーブルに記録した関係であり、リンクは参照先へ移動するための手段です。

仕様や設計を変更するときは、次の点を確認します。

1. 変更する情報の正本を特定し、そこで変更内容を確定する。
2. 対象・条件・例外・期待結果など、変更前後の意味の差を確認する。
3. 識別子の同一性と、Relationships の参照先・意味を確認する。
4. 参照元や関連する要求・設計・契約・検証条件との整合性を確認する。記録されていない依存関係も必要に応じて調べる。

識別子やリンクが正しく解決できても、仕様同士の意味が整合するとは限りません。変更後も、関連する定義と検証条件が有効であることを確認します。

### 4.1 変更の種類と逆引きする参照元

参照元は、変更の種類ごとに次のように逆引きします。

| 変更 | 逆引きする参照元 | 確認すること |
|---|---|---|
| 表現の修正 | なし | 条件・範囲・例外の意味が変わっていないか |
| 見出しの変更・ファイルの移動 | 本文中のリンク、Relationship テーブルの Target、`llms.txt` | リンクが切れていないか。識別子は維持する |
| 機能要求・品質要求・不変条件の意味の変更 | その識別子を Target とする `alignment` を持つセクション、本文中の言及、その識別子を `//trace:checks` で宣言したテスト、ユーザーガイドの文書のうち References に要求定義を挙げるものか、その識別子に言及するもの | 参照元が変更後の条件と整合するか。テストの検査条件と期待結果が変更後の意味に合うか |
| CLI 仕様・表示仕様・YAML 設定仕様の変更 | その文書を参照する設計の節、関係するテスト、References にその文書を挙げるユーザーガイドの文書 | 設計と実装が変更後の契約を前提にしているか。ガイドの説明と出力例が変更後の契約と食い違わないか。YAML 設定仕様のキーか値を足すか変えたなら、[設定ファイルのインターフェイス設計方針](configuration-policy.md) 8章の点を確かめたか |
| ドメインモデルの用語の意味の変更 | その概念を平易な語で説明しているユーザーガイドの文書。関連リソースの概念（存在の観測、作成、削除、存在しないことの宣言、同一性）では、加えて、要求定義の「対象範囲」と `FR-001`、YAML 設定仕様 2.1節、アーキテクチャ設計 3.2節・5.3節、GitHub API 通信の設計 2.3節・2.4節、関連リソースを扱う設定ごとの設計 | ガイドの説明が、変更後の意味と食い違わないか。関連リソースの概念では、宣言していない関連リソースを変えない範囲と、削除する条件が、どの文書でも同じか |
| 表示の文言の変更（外部契約の範囲を変えないもの） | 出力例か出力の行を引用するユーザーガイドの文書 | ガイドの出力例と説明が、`make build` した実行ファイルの出力と食い違わないか（5.6節）。文言の変更で、行が伝えなければならない情報（表示仕様、設定ごとの設計）を落としていないか |
| 関連リソースの種類の追加、または種類ごとの操作（作成、削除）の追加 | 要求定義の「対象範囲」のサポート対象とサポート対象外、YAML 設定仕様 2.1節、表示仕様 3章・4章・5章、アーキテクチャ設計 3.2節・5.3節、GitHub API 通信の設計 2.3節・2.4節・4章、その種類が属する設定ごとの設計、ユーザーガイドの概要・設定ファイルの書き方・安全性の約束 | サポート対象が実装と合うか。宣言していない関連リソースを宛先とする更新要求がないか。削除は、存在しないことの宣言がある名前に限られているか |
| 値が解釈しない部分を含み得る設定の追加、または解釈する範囲の変更 | その設定が属する設定ごとの設計の「観測」と「適用可能性と副作用」、ドメインモデル 4.3節・4.4節、アーキテクチャ設計 3.2節・5.3節、GitHub API 通信の設計 2.1節、YAML 設定仕様のその設定の章、表示仕様の比較不能と適用不能と `show` の確認できない値の表示 | 観測で解釈する範囲が、宣言で受け付ける範囲をすべて含むか。解釈しない部分を含む値を、観測操作の失敗にも、除いた残りの観測値にもしていないか。その値を置き換える更新要求を、適用可能にしていないか |
| 扱う設定の追加、または設定ごとの設計の変更 | その設定が属する設定ごとの設計（トップレベルのキーが新しければ文書を足す）、その文書を参照する表示仕様・YAML 設定仕様の本文、その文書の節を名前で参照する Go のコメント | ドメインモデル、アーキテクチャ設計、GitHub API 通信の設計、変更の実行の設計に、その設定に固有の規則を書き足していないか。CLI 仕様と表示仕様に、その設定の名前、値の表記、適用不能の条件、副作用、実行順などを書き足していないか。YAML 設定仕様に、宣言だけから決まらない判断を書き足していないか。一般の規則で足りない判断が要るなら、先にドメインモデルかアーキテクチャ設計で一般の規則として採否を決めたか。設定ごとの設計に、一般の規則の言い直しやコードを読めば分かることを書いていないか |
| GitHub API 仕様の変更 | 変更した GitHub API 仕様の文書を Target とする `grounding` を持つすべてのセクション | 主張が引き続き根拠に支持されるか |
| リリースワークフロー設計の変更 | References にリリースワークフロー設計を挙げるユーザーガイドの文書 | アーティファクトの名前と種類、イメージのタグ、利用者による検証の手順の説明が、変更後の設計と食い違わないか |

参照元のうち Relationship テーブルと `//trace:checks` は、`sdlc trace` で洗い出せます（4.4節）。`sdlc trace --id FR-008` は、その識別子を参照するセクションとテストを返し、参照元が定義ならその参照元も辿ります。`sdlc trace --file docs/research/repositories.md` は、そのファイルを Target とするセクションを返します。本文中の言及、本文中のリンク、ユーザーガイドの References、`llms.txt` は Relationship ではないため候補に現れず、これまでどおり別に探します。

`grounding` の Target はファイル単位で書くため、GitHub API 仕様の変更では、変更した節に依存しない箇所も逆引きの候補に含まれます。本文中に `[GitHub リポジトリ API 仕様](../research/repositories.md) 4章` のような節番号を添えたリンクがあれば、変更した節に依存する箇所を先に特定する手がかりになります。ただし、節番号を添えずに依存している箇所もあるため、節番号のない候補も、主張が変更した節に依存していないかを確認します。

テストが合格しても、検査条件が変更後の意味に合っているとは限りません。テストは変更前の意味を前提に書かれており、意味を変えた後も合格し続けることがあるためです。`//trace:checks` で宣言したテストは、合格していても期待結果を読み直します。

### 4.2 新しく見つかった制約の正本

実装、GitHub API の実際の動作の確認、テストの失敗などで新しい制約が見つかった場合は、見つけた場所に規範を書き足しません。見つけた場所に書くと、正本の外に正本と食い違い得る規範が生まれるためです。要求定義・CLI 仕様・表示仕様・YAML 設定仕様・GitHub API 仕様のうち、その制約に責務を持つ正本で採否を決めてから、参照元を合わせます。

### 4.3 確認の深さ

変更が安全性の保証にどれだけ関わるかによって、確認の深さを変えます。

| 深さ | 対象 | 確認の中心 |
|---|---|---|
| 重点 | 不変条件全般、`QR-001`、HTTP リダイレクトの扱い、更新操作の結果判定（[GitHub API 通信の設計](../design/github-access.md) 3.1 の表）、未管理設定の保全（[アーキテクチャ設計](../design/architecture.md) 5.3 と、[設定ごとの設計](../design/settings/README.md) の各文書の「更新方式」） | 条件を緩めていないかの差分確認、失敗シナリオ、根拠との照合。条件を緩める変更は人間が判断する |
| 標準 | 重点以外の機能要求・品質要求、CLI 仕様、表示仕様、YAML 設定仕様 | 4.1 の逆引き、境界例と例外 |
| 軽量 | 表現の修正、見出しの変更、ファイルの移動 | リンクと構造 |

重点の対象は、条件を緩めてもテストが失敗するとは限らず、緩めた結果が誤った更新や認証情報の漏えいとして現れる定義です。

### 4.4 sdlc による検査

2章の識別子と3章の Relationships の書き方は、`sdlc` で検査します。`sdlc` は、リポジトリ直下の `sdlc.yaml` に従って、要求定義の定義見出し、`docs/` 配下の Relationship テーブル、Go ファイルの `//trace:checks` を読みます。文書や宣言を変えたら、リポジトリ直下で次を実行し、違反が0件であることを確かめます。

```console
sdlc validate --config sdlc.yaml
```

`validate` が検査するのは書き方と参照の解決であり、4章冒頭の意味の整合は検査しません。違反が残っていると、`sdlc trace` は候補を返さずに失敗します。違反のある宣言を読み飛ばすと、候補が欠けたまま正常に見えてしまうためです。

`sdlc.yaml` の `allowed_dependencies` は、1章の依存の向きを Relationship について検査します。GitHub API 仕様（`docs/research/`）の Relationship の Target は GitHub API 仕様とスクリプト（`scripts/`）に限り、ユーザーガイド（`docs/user-guide/`）には Relationship を置きません（5.2節）。本文中のリンクと References は Relationship ではないため、この検査の対象外です。

`sdlc.yaml` の `scan.go` は、Go ファイルを探す範囲をリポジトリ直下、`cmd/`、`internal/` に絞っています。Go のテストを別のディレクトリに足すときは、`scan.go` にも足します。足さないと、そのテストの `//trace:checks` は検査されず、`trace` の候補にも現れません。

## 5. ユーザーガイド

ユーザーガイド（`docs/user-guide/`）は、reco の利用者が読む文書です。ほかの文書とは読者が違うため（1章）、書き方の規則もこの章で別に定めます。

### 5.1 読者

ガイドの読者は、GitHub の個人アカウントで複数のリポジトリを持ち、設定画面の項目をある程度知っている人です。Go や GitHub REST API の知識、reco の実装やドメインモデルの知識は前提にしません。

読者は文書を通読せず、いま抱えている問い（自分の管理したい設定を扱えるか、どう入れるか、どう書くか、止まったらどうするか）の答えだけを探します。ガイドは、reco を初めて使う人がこの答えを最小の労力で得られることを最優先にします。そのため、80% の読者が出会う事実を書き、それ以外は詳細文書（5.4節）か、References に挙げる正本に任せます。正確でも量の多い文書は、答えを探す手間を増やし、読まれなくなります。

### 5.2 正本との関係

ガイドは正本（要求定義、CLI 仕様、表示仕様、YAML 設定仕様、設計文書、GitHub API 仕様。アーティファクトと検証の手順については [リリースワークフロー設計](release.md)）を利用者向けに説明する文書であり、新しい規則を書きません。ガイドと正本が食い違えば正本が優先し、ガイドのほうを直します。ガイドを書く途中で正本の誤り、正本どうしの食い違い、正本にない制約を見つけた場合は、ガイドに規則を書き足さず、4.2節に従って正本で採否を決めます。

ガイドの構成と語は、正本の章立てや用語ではなく、利用者の作業の順と平易な言葉に合わせます。正本の構成と書き方は、ガイドのために変えません。

ガイドが説明している正本と、ガイドの外の参照先（Issue など）は、各文書の末尾の References に集め、項目ごとにそこで確かめられることを一言添えます。正本を変えるときの逆引き（4.1節）は、この References を手がかりにします。ガイドのセクションには Relationship テーブルを置きません。

ガイドは `docs/` 配下のほかの文書と同じく日本語で書き、英語版は作りません。リポジトリ直下の README は英語のまま、ガイドへのリンクと最小の使い方の例だけを置きます。README の使い方の例は [Getting Started](../user-guide/getting-started.md) と食い違わないようにします。

### 5.3 書き方

- **書く事実**：読者の行動か判断を変える事実だけを書く。各セクションは、読者の問い一つに答える。同じ種類の例は一つに絞る
- **例外と条件**：多くの読者が出会わない条件、例外、境界（入力検証の細則、内部の仕組み、待ち時間の決め方など）は書かない。reco の実行が完了すれば残らない状態（一つの変更の更新のあいだの状態など）も、読者が何もできないため書かない。言い切ると誤りになる事実は、条件を足して守るのではなく、その事実を書かないことで守る
- **断り書き**：reco がしないこと、確かめていないこと、保証しないことを、読者が問う前に書かない。読者が実際に出会う制約は、その制約に出会う場面で、事実として一文で書く
- **語**：平易な語で書く。ドメインモデルや要求定義の術語（期待状態、観測不能、変更前提、論理的な設定変更など）は使わず、その働きを普通の言葉で書く。ただし、reco の出力に現れる語（`updated`、`failed`、`not attempted` など）は、出力のとおりに書く
- **リンク**：本文に置くリンクは、読者が次にする作業の文書へのものだけにする。根拠や補足へのリンクは置かない。ガイドの外へのリンクは References だけに置く
- **重複**：読者の動線の上で要る事実は、ほかの文書と重なっても短く書いてよい。読者を別の文書へ往復させるより、その場で一文を読ませるほうが少ない労力で済むためである。ただし、一つの事実を二つの文書で詳しく説明することはしない
- **出力の注意書き**：通常の出力の行に、読み違えを防ぐ注意書きが要ると感じたら、注意書きを足す前に、その行が利用者の理解（いま何が効いていて、承認すると何が起きるか）に沿っているかを疑う。沿っていなければ、ガイドで補わず、表示を直す。行が伝える情報が足りなければ 4.2節に従って表示仕様か設定ごとの設計で採否を決め、文言だけの問題ならコードの文言を直す。注意書きで補った出力は、ガイドを読まない利用者には伝わらないためである

誤った記述を書かないことは、分量を減らすかどうかにかかわらず守ります。分量を減らすのは、読者に要らない事実を書かないことによってであり、事実を不正確に丸めることによってではありません。

### 5.4 文書の構成

ガイドの文書は、初めて使う人が上から順に読む **主な文書** と、関心を持つ人だけが読む **詳細文書** に分けます。主な文書は、詳細文書を読まなくても reco を使えるように書きます。詳細文書へのリンクは、主な文書の該当する場面に一つだけ置きます。

| 区分 | 文書 | 書くこと |
|---|---|---|
| 入口 | [reco ユーザーガイド](../user-guide/README.md) | 目的ごとに読む文書。主な文書と詳細文書を分け、読んでほしい文書ほど上に並べる |
| 主な文書 | [Overview](../user-guide/overview.md) | 導入の判断に要る結論（解決する問題、基本の流れ、管理できる設定と、設定画面の項目と設定ファイルのキーの対応） |
| 主な文書 | [Installation](../user-guide/installation.md) | reco をインストールして `GH_TOKEN` を渡して動かすまでの手順 |
| 主な文書 | [Authentication](../user-guide/authentication.md) | `gh auth token` のトークンの渡し方と、トークンの持ち主に要るロール |
| 主な文書 | [Getting Started](../user-guide/getting-started.md) | 一つの設定で `show`、`plan`、`apply` を試す一本道の手順。手順の途中にリンクを置かず、参照先は References にまとめる |
| 主な文書 | [Configuration](../user-guide/configuration.md) | 設定ファイルの構造、設定項目ごとのキー・値・意味、未記載の設定の扱い、複数のリポジトリの並べ方、よくある書き方の誤り |
| 主な文書 | [Commands](../user-guide/commands.md) | コマンドとオプション、各コマンドの実行例と通常の出力の読み方、承認、認証情報の環境変数、出力先、終了コード |
| 主な文書 | [Operations](../user-guide/operations.md) | リポジトリを管理に加える、対象を絞る、並べる順序、定期的な確認、値を戻す、管理をやめる手順 |
| 主な文書 | [Troubleshooting](../user-guide/troubleshooting.md) | エラーや失敗時の出力ごとの、その行の意味、原因の候補、次にすること |
| 詳細文書 | [Safety](../user-guide/safety.md) | reco が設定を変えるときに安全を保つ仕組みと、reco がしないこと |
| 詳細文書 | [Verification](../user-guide/verification.md) | `gh attestation verify` によるVerification |

一つの事実をどの文書で詳しく説明するかは、この表の「書くこと」で決めます。ほかの文書は、5.3節の「重複」の範囲で短く触れるだけにします。

### 5.5 文書を足すか変えるときの確認

ガイドの文書を足すか変えるときは、既存のガイドの全文書について次の点を確かめ、既存の文書を直す必要があれば同じ変更で直します。

- 5.3節の書き方を守っているか（断り書き、術語、根拠や補足へのリンクがないか）
- 一つの事実を二つの文書で詳しく説明していないか
- 記述が互いに食い違っていないか
- 説明している正本が References にあるか

文書を足したときは、5.4節の表、ガイドの README の「目的から選ぶ」、`llms.txt` にも足します。

### 5.6 出力例と設定画面の項目名

ガイドに載せる `show`、`plan`、`apply` の出力例とエラーは、`make build` した実行ファイルの出力から取ります。表示仕様の表示例は形を示すためのもので、文言と細かい表記を外部契約としないため（[表示仕様](../spec/output.md) 1章）、ガイドの出力例の出典にはしません。実際の出力が、表示仕様の構造、固定の語、伝える情報と食い違う場合は、正本と実装の食い違いであり、4.2節に従って正本で採否を決めます。出力の文言を変えたときは、その出力を引用するガイドの文書を同じ変更で直します（4.1節）。

表示仕様に定めがあっても、現在の reco が出力する経路のない出力は書きません。読者が出会わない出力を説明すると、読者は自分の出力にその行がないことを異常と読み違えるためです。

設定と GitHub の設定画面の項目の対応を示すときは、[GitHub API 仕様](../research/README.md) に出典とともに書かれた項目名だけを使います。設定画面の項目名は GitHub の事実であり、正本は GitHub API 仕様だからです。必要な項目名が書かれていなければ、GitHub の公式資料で確かめて GitHub API 仕様に追記してから使い、確かめられなければ書きません。
