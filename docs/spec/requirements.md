# 要求定義

本ドキュメントは、reco が提供する機能、利用者から観察できる振る舞い、品質上の保証と適用範囲を規定します。

## 1. 目的

reco（Repository Configurator）は、利用者が指定した GitHub リポジトリについて、現在の設定状態を把握し、明示した期待状態との差を確認したうえで、必要な設定変更を適用する CLI です。多数のリポジトリの設定を記憶・確認・変更する負担を軽減し、利用者の意図に沿った管理を支援します。

## 2. 対象範囲

reco は GitHub.com を対象とし、利用者が指定した個人アカウント所有のリポジトリを扱います。利用者は、対象に必要な権限を持つ認証情報を用意します。ただし、個人アカウント所有であることは利用者が守る前提であり、reco は認証主体とリポジトリ所有者の一致を検証しません。

利用者は、リポジトリごとに管理する設定と期待状態（Desired State）を、設定宣言（Configuration Declaration）として明示します。各リポジトリについて、期待状態が明示された設定の集合を管理範囲（Management Scope）と呼びます。

GitHub 上に実際に存在する設定を現在状態（Current State）と呼び、reco がある時点で確認できた情報とその範囲を観測結果（Observation Result）と呼びます。観測結果は現在状態のすべてを含むとは限りません。

利用者が reco に要求する操作は、状態確認、変更計画の確認、設定変更の三つです。
変更計画の確認と設定変更では、設定宣言と観測結果から変更計画（Change Plan）を作成します。

利用者が意図する変更内容と、完了を判断する期待状態とが対応する変更の単位を、論理的な設定変更（Logical Change）と呼び、GitHub に対する個々の更新要求を更新操作と呼びます。
一つの論理的な設定変更は、複数の更新操作で実現される場合があります。

### サポート対象

| 分類 | 対応する設定 |
|---|---|
| リポジトリ一般設定 | Pull Request の Auto-merge の許可、マージ後のブランチ自動削除の許可 |
| GitHub Actions 設定 | Actions と再利用可能なワークフローの実行許可範囲および個別の許可条件、ワークフローの `GITHUB_TOKEN` の既定権限、GitHub Actions による Pull Request の作成と承認の許可 |

### サポート対象外

- Organization 所有リポジトリ・GitHub Enterprise Server
- 宣言されていないリポジトリの自動発見
- リポジトリや関連リソースを直接作成・削除する操作
- 設定の望ましさの独自評価や、セキュリティ改善策の自動提案
- 承認を省略した設定変更
- GitHub REST API の HTTP リダイレクトへの追従

## 3. 機能要求

### FR-001 設定宣言の受け入れと検証

利用者が設定宣言を指定した場合、reco は宣言されたリポジトリ、管理する設定、期待状態を解釈し、宣言全体を検証します。宣言には少なくとも一つのリポジトリ指定を含め、指定した各リポジトリについて少なくとも一つの管理設定を定めます。利用者が実行時の対象を一つのリポジトリに絞る場合も、宣言全体の検証は省略しません。

設定宣言で明示された設定だけを管理対象とし、無効化や空集合を含め、明示された値を期待状態として扱います。
省略された設定を、無効化、空集合、値の不存在、既定値への復元として補完しません。

入力が不正、矛盾している、または設定の意味を確定する情報が不足している場合は、問題の対象と理由を示して拒否し、設定変更を開始しません。意味を確定するために必要な情報のまとまりは、設定の性質に応じて判定します。

同じリポジトリを指す指定が複数ある場合は、入力不正として拒否します。
所有者名とリポジトリ名は、大文字小文字を区別せずに比較します。

### FR-002 対象リポジトリの選択

利用者が変更計画の確認または設定変更を要求した場合、reco は設定宣言で指定された全リポジトリ、または利用者がその中から明示した一つのリポジトリを対象とします。設定宣言に含まれないリポジトリを対象に追加しません。

### FR-003 認証情報の利用

reco は、利用者が用意した認証情報を使って対象リポジトリへアクセスします。認証情報が利用できない場合や認証に失敗した場合は、その問題を報告し、設定変更を開始せずにエラー終了します。reco 自身は認証情報を発行・保存せず、認証失敗を理由に利用者が選択していない別の認証情報へ暗黙に切り替えません。

### FR-004 現在状態の取得と表示

reco は、各操作に必要な設定情報を、対象リポジトリについて GitHub から取得します。利用者が状態確認を要求した場合は、設定宣言を必要とせず、指定したリポジトリについて確認できた設定情報を表示します。この確認操作では GitHub の設定を変更しません。

reco は取得時点に確認できた情報と、GitHub の取得条件によって確認できない情報を区別し、未確認の値を推測・補完しません。取得条件による観測不能と、認証・権限・通信などによる観測操作の失敗を区別します。観測操作に失敗した場合は、対象と理由を報告してエラー終了します。読み取り要求に対する GitHub API の HTTP リダイレクト応答は、取得条件による観測不能ではなく観測操作の失敗として扱い、追従しません。

### FR-005 期待状態と観測結果の照合

変更計画を作成する際、reco は管理範囲内の期待状態と観測結果を比較し、次の結果を区別します。

- **一致（Match）**：観測できた現在値が期待状態と一致する。
- **不一致（Mismatch）**：比較可能な現在値と期待状態が異なる。
- **比較不能（Not Comparable）**：取得条件によって必要な現在値を観測できず、一致・不一致を判断できない。

現在値が期待状態と一致する設定も管理範囲に含めるが、変更を必要とする設定とは区別します。管理対象外の設定は照合しません。観測操作自体が失敗した場合は、比較不能として処理を続けず、照合が完了したものとみなしません。

### FR-006 変更の適用可能性の判断

変更計画を作成する際、reco は、不一致または比較不能と判定されたすべての設定について、変更の適用可能性を照合結果とは別に判断します。必要な情報、確認可能な権限条件、未管理設定の保全、変更途中の影響を踏まえ、安全な変更に必要な条件を確認できない場合は、適用不能として理由を示します。

不一致でも条件を確認できなければ適用不能とし、比較不能でも条件を満たせば適用可能とします。
事前に権限不足が見つからなかったことは、実行時の成功を保証するものではありません。

### FR-007 変更計画の確認

利用者が変更計画の確認を要求した場合、reco は設定宣言と現在の観測結果に基づいて変更計画を作成し、対象と変更内容、適用可否を提示します。確認できた差分、比較不能だが設定を予定する項目、適用不能な項目を区別し、適用できない理由を確認できるようにします。この確認操作では GitHub の設定を変更しません。

### FR-008 変更前の全対象検証

利用者が設定変更を要求した場合、reco はその時点の設定宣言と GitHub の観測結果に基づいて変更計画を確定し、選択された対象全体について変更前に確認可能な問題を検証します。
入力不正は、GitHub へ問い合わせる前に宣言全体を検証して報告します（FR-001）。
観測操作に失敗した場合は、その時点で検証を打ち切ります（FR-004）。
適用不能な変更は、選択された全対象の検証を終えたうえで、対象と理由をまとめて報告します。
問題が一つでも見つかった場合は、更新を開始せずにエラー終了します。

管理範囲内のすべての設定が一致と判定された場合は、承認を求めず、設定を変更しないで終了します。

### FR-009 設定変更の明示的な承認

設定変更が必要な場合、reco は対象と変更内容を利用者に提示し、対話的な明示承認を求めます。現在値を比較できない設定については、その不確実性も提示します。承認が得られない場合、または対話的に承認できない場合は、その結果を利用者に報告します。

### FR-010 承認後の変更前提の再確認

reco は、承認した変更対象と内容を維持し、変更を実行する前提が成立していることを確認します。前提には、対象リポジトリの同一性、変更に関係する現在状態と適用条件を含めます。複数の更新操作からなる論理的な設定変更では、承認された先行操作による予定どおりの状態変化を考慮し、それだけを前提不成立とは扱いません。前提を確認できない場合や、関係する予定外の変化を検出した場合は、変更内容や対象を黙って差し替えず、当該更新を開始しません。更新を開始しなかったことを、対象・理由とともに報告します。

### FR-011 期待状態を実現するための設定変更

reco は、管理範囲内で、不一致が確認された設定、または比較不能であっても適用可能と判断して変更計画に含めた設定を対象に、期待状態を実現するための変更を行います。期待状態との一致を確認した設定だけを理由とする更新は行いません。別の管理設定の変更に必要な更新操作で既存値を送信しても、その設定を新たな変更対象とは扱いません。

### FR-012 変更後の期待状態の確認

設定を変更した場合、reco は変更後の状態が期待状態と一致することを確認して、完了を判断します。
更新操作の成功応答だけでは完了と判断しません。
一つの論理的な設定変更を複数の更新操作で実現する場合は、必要な更新操作の結果を確認したうえで、その全体の期待状態を確認します。更新操作の成否と期待状態の確認結果を区別し、必要な更新操作の成功と期待状態の一致の双方を確認できない限り、論理的な設定変更を完了として報告しません。
更新操作によって影響を受け得る未管理設定のうち再取得できるものは、更新直前に確認した値から変化していないことも確認します。

### FR-013 変更結果と異常の報告

reco は、設定変更の結果を、論理的な設定変更ごとに次の区分で報告します。

- **完了**：期待状態との一致を確認でき、未管理設定の予期しない変化を検出しなかった。
- **失敗**：更新を開始したが、完了を確認できなかった。
- **未実行**：更新を開始しなかった。

失敗については、次のいずれに当たるかを示します。

- 更新操作の失敗
- 更新操作の成否不明
- 成功応答後の期待状態の確認失敗
- 成功応答後の期待状態との不一致
- 成功応答後の未管理設定の予期しない変化
- 先行する更新操作の成功後に、後続の更新操作を開始できなかったこと

未管理設定の予期しない変化は、外部主体による同時変更の可能性もあるため、reco に起因すると断定しません。
未実行については、承認時の前提の不成立や、先行する異常による停止などの理由を示します。
既に実施した変更を自動的に元へ戻しません。

更新操作の応答が失われた場合と、更新要求に対して GitHub API から HTTP リダイレクト応答を受け取った場合は、更新操作の成否不明とし、更新操作の成功・失敗のいずれとも断定しません。
リダイレクト応答には追従しません。
失敗した論理的な設定変更が一つでもある場合は、エラー終了します。

## 4. 品質要求

### QR-001 認証情報の秘匿

reco は、正常時・異常時を問わず、利用者が提供した認証トークンや認証ヘッダーの秘密情報を、画面出力、エラー情報、ログに表示・記録しません。

### QR-002 結果と診断情報の判別可能性

reco は、設定状態、変更計画、変更結果、処理を続けられない理由を、利用者が対象とともに判別できる形で示します。実際に確認できた事実と不明な情報、取得条件による観測不能と観測操作の失敗、更新操作の成否と期待状態の確認結果を混同しません。

## 5. 不変条件

### INV-001 管理範囲外の設定の保全

reco が設定変更を行う場合、設定宣言の管理範囲に含まれない設定や別リソースを自身の変更対象として選択せず、更新操作によって暗黙に変更・削除しません。外部サービスの制約により未管理設定の既存値を更新操作へ含める必要がある場合も、その値を維持できる条件を確認できなければ当該更新を開始しません。既存値を併送しても、その設定を新たな管理対象にはしません。

この制約は reco 自身の更新操作を対象とし、外部主体による同時変更や GitHub 側で独立して発生する状態変化まで防ぐものではありません。

### INV-002 全対象の事前検証を経ない更新の禁止

一回の設定変更の実行において、選択された全リポジトリについて変更開始前に確認可能な問題の検証が完了し、入力不正、観測操作の失敗、適用不能な変更など、検出された問題が残っていないことを確認するまでは、どの対象についても更新を開始しません。

### INV-003 未承認の設定変更の禁止

一回の設定変更の実行において、変更対象と内容を利用者に提示し、その内容について対話的な明示承認を得るまでは、更新を開始しません。承認が拒否された場合、または対話的な承認が得られない場合も、更新を開始しません。

### INV-004 承認時の前提に反する変更の禁止

承認された論理的な設定変更を構成する各更新操作は、その開始直前に、承認したリポジトリと同じ実体を対象としていること、必要な現在状態と適用条件を確認できた場合に限り開始します。前提の判定には、承認された先行操作によって到達する予定状態を含め、予定どおりの状態変化だけを理由に停止しません。一方、対象の同一性の不一致、当該操作の前提に関係する予定外の状態変化、適用条件の不成立、必要な情報の取得失敗などによって前提を確認できない場合は、対象や変更内容を黙って差し替えず、当該操作および後続の更新を開始しません。

### INV-005 異常検出後の更新継続の禁止

一回の設定変更の実行において、更新操作の失敗、更新操作の成否不明、変更前提の不成立、変更後の期待状態の確認失敗・不一致、未管理設定の予期しない変化を検出した後は、新たな更新を開始しません。一つの論理的な設定変更を構成する更新操作は、先行する更新操作の成功を確認した場合に限り続行できます。また、その論理的な設定変更の期待状態が確認できるまで、別の論理的な設定変更の更新を開始しません。成否を確認できない更新要求は再送しません。
